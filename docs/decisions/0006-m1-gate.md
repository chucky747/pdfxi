# ADR 0006 — M1 gate scope and honest milestone rows

- Status: accepted
- Date: 2026-11-19

## Context

`docs/PLAN.md` defines M1 as a vertical slice: parse headers, xref tables and
streams, the object graph and filters; render pages through PDFium; open,
navigate, zoom, search, select, and copy text; CLI `info`, `text`, `render`;
save round-trip; 50 generated fixtures; first benchmarks. Printing is listed
under M2.

The feature matrix nevertheless bundles opening and printing into one row
(`VIEW-001`). Requiring `VIEW-001` for the M1 gate would force M2 print work
into M1, or tempt us to mark a row verified while its print half is missing.
Both are dishonest.

## Decision

1. M1's gate requires rows that match M1 scope exactly:
   `STD-011`, `STD-012`, `AUTO-009`, `AUTO-010`, `VIEW-002`, `VIEW-003`,
   `VIEW-016`, plus the milestone exit benchmark recorded in
   `docs/evidence/M1.md`.
2. A new row `VIEW-016` ("Open PDF and render pages in the viewer") carries the
   M1 open/display slice. `VIEW-001` keeps its original open-and-print scope and
   stays in-progress until printing lands in M2.
3. No row may be marked verified for functionality that only exists as a model,
   contract, or placeholder. In-progress is the default for partial slices.
4. The M1 exit benchmark (500-page open under 1.5 s, first page under 300 ms)
   must be recorded with command output in `docs/evidence/M1.md` before the
   milestone is declared verified.

## Consequences

- The gate can go green without claiming print parity.
- `cargo xtask goal-verify --all` still requires every matrix row, including
  `VIEW-001`, to be verified or explicitly replaced later.
- Reviewers can reject a row promotion that lacks end-to-end evidence.
