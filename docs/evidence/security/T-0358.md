# T-0358 — Certificate encryption host (`SEC-003`)

Row promoted: `SEC-003` (Certificate encryption) `model` -> `verified`.

The row had the complete enveloped-content model: AES-CBC content encryption,
one wrapped content-encryption key per recipient, a SHA-256 key commitment, a
typed recipient list, sender-granted permissions and RFC 3394 AES-KW. Its own
note stated the boundary: "RFC 3394 AES-KW content-key wrapping with
authenticated integrity check and typed errors; recipient public-key unwrap is a
documented provider boundary." This task supplies that provider and a host.

RSA decryption is deliberately **not** used: the repository's scoped
RUSTSEC-2023-0071 ignore is honest only while `pdfxi-security` has no RSA
decryption path, and a scoped guard test enforces that. Recipient key transport
is therefore ephemeral ECDH over P-256 with HKDF-SHA256, which needs no RSA
private-key operation.

## 1. Library additions

- `EcdhKeyWrapProvider`: a real certificate-addressed key-wrap provider.
  - `sealing()` generates an ephemeral P-256 key, performs ECDH with the
    recipient certificate's EC public key, derives a 256-bit KEK with
    HKDF-SHA256 (info `pdfxi-ecdh-aeskw-v1`), and wraps the CEK with RFC 3394
    AES-KW. The wrapped value is `ephemeral SEC1 point (65) || AES-KW output`.
  - `unsealing(private)` checks that the private key matches the supplied
    certificate, repeats the agreement and unwraps.
  - Debug output reports only whether a private key is present.
- `RecipientEnvelopeKey::new` rebuilds a persisted recipient entry and rejects
  empty fields with a typed error.
- `EnvelopedData::new_parts` rebuilds an envelope from persisted parts and
  re-checks the non-empty recipients/ciphertext/commitment invariants;
  `iv()`, `key_commitment()`, `ciphertext()` and
  `RecipientEnvelopeKey::wrapped_key()` expose the opaque bytes needed for
  persistence. Nothing is logged.
- A unit test builds a real P-256 certificate (canonical DER, real SPKI), seals
  32 bytes, opens with the matching key, rejects a different key, rejects a
  replaced wrapped key, and rejects empty persisted parts.

## 2. Host

```text
pdfxi recipient seal FILE --out ENVELOPE.json --cert CERT.pem [--cert ...]
    [--cipher aes256-cbc|aes128-cbc] [--permissions print,copy,...]
    [--cek-hex HEX] [--iv-hex HEX] [--json]

pdfxi recipient open ENVELOPE.json --key KEY.pem --cert CERT.pem --out FILE
    [--require PERMISSION] [--json]
```

- A fresh 128/256-bit content key and 16-byte IV come from the OS random source
  unless `--cek-hex`/`--iv-hex` pin them for reproducible runs.
- Recipient labels are certificate subjects; duplicate certificates are
  rejected by the model.
- The portable container stores the format/version, cipher, IV, one wrapped key
  per recipient, ciphertext, key commitment and permission bits as JSON.
- `open` finds the entry for the supplied certificate fingerprint, rebuilds the
  envelope through `new_parts`, unwraps the CEK with `EcdhKeyWrapProvider`,
  checks the key commitment and CBC content, optionally requires one granted
  permission, and writes the plaintext.
- A container not addressed to the certificate, a replaced wrapped key, a
  denied permission, malformed containers and bad keys are typed errors.

## 3. Evidence

```text
> pdfxi recipient seal target\tmp\recipient\payload.txt
    --out target\tmp\recipient\payload.envelope.json
    --cert target\tmp\recipient\recipient-cert.pem
    --cek-hex 1111...11 --iv-hex 2222...22 --permissions print,copy --json
{
  "out": "target\\tmp\\recipient\\payload.envelope.json",
  "bytes": 732,
  "cipher": "aes256-cbc",
  "plaintext_bytes": 29,
  "recipients": ["CN=PDFXI Recipient Evidence,O=PDFXI"],
  "wrapped_lens": [105],
  "ciphertext_bytes": 32,
  "permissions": 20,
  "permission_names": ["print", "copy"]
}
EXIT=0

> pdfxi recipient open target\tmp\recipient\payload.envelope.json
    --key target\tmp\recipient\recipient-key.pem
    --cert target\tmp\recipient\recipient-cert.pem
    --out target\tmp\recipient\payload.out --require copy --json
{
  "out": "target\\tmp\\recipient\\payload.out",
  "bytes": 29,
  "recipient": "CN=PDFXI Recipient Evidence,O=PDFXI",
  "permissions": 20,
  "permission_names": ["print", "copy"],
  "required": "copy"
}
EXIT=0
```

The recovered file is byte-identical to `payload.txt` ("certificate-addressed
payload"). The 29-byte plaintext becomes a 32-byte padded ciphertext, and the
wrapped key is 105 bytes: a 65-byte uncompressed P-256 ephemeral point plus the
40-byte AES-256-KW wrapping of the 32-byte CEK.

## 4. Tests

```text
> cargo test -p pdfxi-security ecdh_key_wrap
certificate_encryption::tests::ecdh_key_wrap_round_trips_with_a_certificate ... ok

> cargo test -p pdfxi-cli recipient_
recipient_seals_and_opens_with_ec_certificates ... ok
recipient_rejects_bad_arguments_and_containers ... ok
test result: ok. 2 passed
```

The CLI round trip seals with pinned CEK/IV, asserts the cipher, plaintext and
ciphertext sizes, one recipient, a 105-byte wrapped key and permissions
`print,copy`, then opens with the matching identity and `--require copy` and
checks the recovered bytes and JSON report. A different certificate reports
"not addressed"; `--require modify` reports permission denied; a container
whose wrapped key is replaced fails unwrap. The second test covers an unknown
cipher, wrong CEK/IV lengths, an unknown permission, a missing input, a
malformed certificate, `{}` as a container and a missing envelope.

The 2 existing RFC 3394 AES-KW tests remain cited and pass, and the scoped
RSA-decryption guard test still passes because no RSA decryption was added.

## Scope

Real certificate-addressed encryption and decryption are user-reachable on real
files: ephemeral ECDH-ES key transport to recipient certificates, AES-CBC
content encryption, multi-recipient containers, key commitment, permission
checks and a portable persisted envelope. Certificate-chain/revocation trust
decisions, hardware key stores and PDF attachment integration remain host/CA
boundaries and are not claimed.
