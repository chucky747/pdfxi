## Independent ISO 32000-2 revision 6 known-answer vector

### Provenance

Generated locally with a throwaway PowerShell script that used **only .NET
`System.Security.Cryptography`** primitives (`SHA256`, `SHA384`, `SHA512`,
`Aes`), with no reference to the `pdfxi-security` Rust code. The generator
implemented ISO 32000-2 Algorithm 2.B directly:

1. `K = SHA-256(password || salt || aux)`.
2. `K1 = (password || K || aux)` repeated 64 times.
3. `E = AES-128-CBC-NoPadding(K1, key = K[0..16], IV = K[16..32])`.
4. `K = SHA-256(E)` / `SHA-384(E)` / `SHA-512(E)` according to
   `(sum of E[0..16]) mod 3` = 0 / 1 / 2.
5. Repeat until `count >= 64` and `E.last <= count - 32`; result is `K[0..32]`.

`/UE` and `/OE` are `AES-256-CBC-NoPadding(file key, intermediate key, zero
IV)`; `/Perms` is `AES-256-ECB-NoPadding(16-byte block, file key)`. The script
was deleted after the vector was recorded; no generator artifact ships in the
crate.

### What the test checks

`revision_6_independent_known_answer_vector_authenticates`:

1. Calls `algorithm_2b` with the .NET-generated seed and asserts the exact
   .NET Algorithm 2.B hash (no crate fixture builder involved).
2. Constructs `SecurityParameters` from the literal `/O`, `/U`, `/OE`, `/UE`,
   `/Perms`, and `/P` values above.
3. Authenticates the user password (validating `/U` and unwrapping `/UE`) and
   the owner password (validating `/O` and unwrapping `/OE`); `verify_perms`
   then checks `/Perms` against `/P` and `/EncryptMetadata`.
4. Rejects a near-miss password.

All assertions passed on the first run; no implementation change was needed.
This removes the earlier circularity, where both fixture construction and the
reader called `hash_r5_r6`.

## Debug redaction

`SecurityParameters` and `StandardSecurityHandler` now implement `Debug`
manually. Byte fields (`o`, `u`, `ue`, `oe`, `perms`, `id_first`) render as
`<redacted>`; numeric/boolean fields (`revision`, `version`, `key_length_bits`,
`p`, `encrypt_metadata`, `aes_streams`) remain visible because they are not
secret. `debug_redacts_dictionary_byte_fields` asserts that none of the hex
encodings appear in either type's `Debug` output. `Decryptor::Debug` already
redacts the file key (separate regression test).

## `verify_perms` timing note (INFO)

`verify_perms` decrypts `/Perms` with the file key and then compares the byte
markers `adb`, the `/EncryptMetadata` flag byte, and the stored `/P` word. These
are public dictionary values or fixed public markers — not passwords, keys, or
other secret material — so their comparisons are intentionally ordinary
(non-constant-time) equality checks. Password validation, by contrast, uses
`crypto::constant_time_eq` on the derived hashes.

## Other independent vector

`revision_5_fixed_vector_decrypt_matches_dotnet_oracle` uses an earlier .NET
AES-256-CBC/PKCS#7 vector: key `0x5A` × 32, IV `01..10`, plaintext ASCII
`"PDFXI AES-256 fixed vector!"`, stored blob `IV || ciphertext`:
`0102030405060708090a0b0c0d0e0f105253bc88496b58583765c97a86ed550e1bfbbfaae7082aeabcc8d8be4621815b`.

## Negative tests

- Wrong passwords (empty, near-miss, wrong case, extra byte) are rejected with
  `SecurityError::WrongPassword` for both revisions 5 and 6.
- A flipped bit in `/Perms`, and a `/P` change without recomputing `/Perms`, are
  rejected for both user and owner passwords.
- A dictionary claiming `EncryptMetadata = true` against a `/Perms` block that
  records `'F'`, and one flipping the R4 `EncryptMetadata` flag while keeping
  the old `/U`, are rejected.
- A 128-bit key length for revisions 5/6, a 16-byte `/UE`, a 128-bit key for R2,
  and a 129-bit key for R4 are rejected with typed `InvalidKeyLength` or
  `Configuration` errors.

## Security notes

- No `unsafe`, no `unwrap`/`expect`/`panic!`/`todo!`/`unimplemented!` in library
  paths, and no secret logging.
- Password comparisons use `crypto::constant_time_eq`; PKCS#7 unpadding checks
  every pad byte in constant time.
- The crate has no OS-entropy dependency; IV randomness is a caller
  responsibility via `encrypt_object_with_iv`, and the deterministic
  `encrypt_object` path is documented as a fixture/compatibility helper.
