## 6. Scope and honesty statement

- SEC-010 is closed **at library level**. `CertificateEnvelope` is created for
  caller-supplied certificate recipients, wraps a single content-encryption key
  once per recipient through the existing `KeyWrapProvider` boundary, records an
  explicit whole-document vs selected-attachments decision in a deterministic
  report, and uses typed errors. Confidentiality is provided by the existing
  AES-CBC + RFC 3394 AES-KW certificate-encryption implementation; no new crypto
  was written. The scope is a declarative decision: this crate never opens a
  document file, so the caller applies the byte-level selection. Host UI/CLI
  exposure is out of scope for the security lane.
- SEC-011 is closed **at library level**. A named `ProtectionPolicy` carries a
  handler, key length, permissions, and recipients; `validate_policy_spec`,
  `build_protection_plan`, and `apply_protection_policy` are deterministic and
  typed. It is an offline local decision model (no rights-management server, no
  network policy fetch, no host clock, no cryptography in the policy itself),
  which the task defines as the accepted replacement.
- No `unsafe`, `unwrap`, `expect`, `panic!`, `todo!`, or `unimplemented!` was
  added to non-test code. No secrets or document contents are logged; byte
  fields are redacted in `Debug` implementations.
- `docs/features.toml` and `orchestration/BOARD.md` were not edited. Feature
  changes are reported in `orchestration/feature-updates/T-0162.toml`.
- Reviewer sign-off and integrator snapshot remain external orchestration steps.
