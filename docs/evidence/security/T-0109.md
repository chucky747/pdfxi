## Behavior verified

- Encrypting save reusing `standard_handler`/`crypto` only: RC4-40 (R2),
  RC4-128 (R3), AES-128 (R4), AES-256 (R6, with R5 accepted) round-trip through
  `pdfxi_core::Document::from_bytes` after password-aware reopen.
- `/Encrypt` dictionary fields: `/Filter /Standard`, `/V`, `/R`, `/Length`,
  `/O`, `/U`, `/P`, plus `/CF`/`/StmF`/`/StrF` for AES and `/OE`/`/UE`/`/Perms`
  for AES-256; trailer carries `/Encrypt` and a two-element `/ID`.
- Strings and streams encrypted with per-object keys; recovered after reopen.
- Wrong password → `WrongPassword`; missing password → `MissingPassword`;
  tampered `/Perms` rejected.
- Permissions `/P` bitmask preserves granted rights and reserved bits; user role
  enforces rights, owner role bypasses them.
- Deterministic output with a fixed seed; existing `/ID` respected, derived ID
  differs from the second ID element.
- Typed `UnsupportedDocumentStructure` errors for signatures, linearized files
  and xref-stream documents.
- Passwords redacted in `EncryptOptions`' `Debug`; no secret logging.

## Notes for the integrator

- Lane permissions for `security` do not grant edit access to
  `crates/pdfxi-core/**`, so no core source was changed. The writer is
  self-contained and calls only public core read APIs
  (`Document::from_bytes`, `object`, `root`, `bytes`, `inspect_xref`).
- Adding the `pdfxi-core` path dependency caused cargo to add one line to the
  integrator-owned `Cargo.lock` (`pdfxi-security` now lists `pdfxi-core`).
- Certificate encryption is a separate feature row and remains out of scope,
  so the SEC-001 fragment is honestly marked `in-progress`.
- No `git` write commands, no network, no new external dependencies, no `unsafe`,
  and no `unwrap`/`expect`/`panic!` in non-test library paths were introduced.
