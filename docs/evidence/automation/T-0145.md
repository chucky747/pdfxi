## Implementation summary

Added `crates/pdfxi-automation/src/action_wizard.rs` and re-exported it from
`crates/pdfxi-automation/src/lib.rs` (module declaration, `pub use` list, and a
module-level doc bullet). No other source file, no shared file, no new
dependency, no network, no `unsafe`, and no non-test `unwrap`/`expect`/`panic!`.

The delivered library-level Action Wizard binding:

- `ActionSequence` — named, ordered, bounded sequence of `WizardStep`s carrying
  a `ScriptBudget`. `validate()` and `add_step()` enforce non-empty sequences,
  non-empty and unique step ids, and `MAX_SEQUENCE_STEPS` (64).
- `WizardStepKind` — `RunScript { script }` (source for the existing parser /
  interpreter), `SetMetadata { key, value }` (in-memory metadata),
  `RunCommand { command }` (named automation command), and `Unsupported { name }`
  (retained so an unknown kind is denied with a typed reason rather than guessed
  into existence).
- `plan_sequence` / `RunnerPlan` / `StepPlan` / `PlanDecision` / `PlanDenyReason`
  — deterministic, non-executing plan with one entry per step in insertion
  order, per-step allow/deny reasons, and exhaustively collected, sorted,
  deduplicated aggregate reasons. Typed deny cases: empty sequence, duplicate
  id, empty id, sequence too long, unsupported kind, empty/oversized script,
  empty metadata key, empty/disallowed command, and budget-over-ceiling fields.
- `ScriptStepExecutor` trait with `SandboxedScriptExecutor` default that wires a
  step's source and `ScriptBudget` into `Script::parse_with_limits` and
  `Script::run` (same cancellation token; wall clock stays disabled). No I/O,
  network, process, clock, randomness, or ambient globals.
- `CommandHandler` trait with `RecordingCommandHandler` default: real command
  dispatch stays the caller's responsibility; the runner performs no I/O.
- `SequenceRunner` / `run_sequence` / `SequenceReport` / `StepRunOutcome` /
  `WizardRunError` — walks the plan in order, skips denied steps, applies
  metadata to an in-memory `BTreeMap`, reports typed success/failure per step,
  and produces byte-stable summaries.
- 17 new tests in `action_wizard::tests::*` cover validation, duplicate/empty
  ids, bounded step count, deterministic plan order and sorted reasons, typed
  per-step deny reasons, unsupported kind, oversized script and budget overage,
  sandboxed script success, typed step-budget exhaustion, pre-cancellation,
  executor success/failure propagation, metadata steps, command success/failure,
  denial skipping without execution, run/plan determinism, and typed
  codes/messages.

## Honest scope / remaining work

At library level the Action Wizard binding is complete. Outside library scope:
there is still no UI Action Wizard editor and no CLI entry point that exposes
these sequences (the CLI `action`/`droplet` commands drive the pre-existing
`Action`/`BatchQueue` model, not this new `ActionSequence` runner). Real
document mutation by script steps is intentionally absent: the JS sandbox
remains capability-free and metadata is kept in memory; command dispatch and
any document effect are owned by the caller through the trait boundaries.
