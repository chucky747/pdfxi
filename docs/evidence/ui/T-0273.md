# T-0273 - `--open-help` launch deep link

## Why

Acceptance item **A-03** (documented shell/automation capture parity) needs the
real viewer to show its Help window in a headless capture. The Help window is
opened from an in-app menu command (`AppCommand::OpenHelp`), and the automation
lane cannot drive menus through synthesised window messages, so a launch flag is
the only reliable way to reach that state in the shipped binary. The flag is a
startup deep link with the same effect as the menu command: it cannot do
anything the real control cannot.

## Flags

| Flag | Effect |
| --- | --- |
| `--open-help` | `LaunchOptions::open_help = true`, opens Help at startup |
| `--help-window` | identical alias |

Both are bare switches with exact lowercase spelling. `--help` (usage switch),
`--open-help=1`, `--help-window=yes`, and `--open_help` are **not** recognised
and leave the flag `false`, so a stray argument can never open a window.

## Changes

- `crates/pdfxi-app/src/settings.rs`
  - `LaunchOptions` gains `pub open_help: bool` with rustdoc explaining the A-03
    reason; the struct keeps `Debug, Clone, PartialEq, Eq, Default`.
  - `LaunchOptions::is_empty()` includes `!self.open_help`, so a help-only launch
    is a real override.
  - `parse_launch_arguments` matches `"--open-help" | "--help-window"`; the doc
    comment lists both forms. Parsing stays exact-match for switches, letting
    `--help` fall through as an unknown flag.
- `crates/pdfxi-app/src/ui.rs`
  - `PdfxiApp::apply_launch_help(bool)` sets `help_open = true`; it is called in
    the `run_native` closure after `apply_launch_tool`, matching the existing
    deep-link order and never persisting anything.
- `crates/pdfxi-app/src/ui.rs` test `help_window_opens_through_the_launch_flag`
  constructs `PdfxiApp::new()`, parses each flag, applies it, and asserts
  `help_open()`; it also asserts a plain app starts closed.

## Tests

`crates/pdfxi-app/src/settings.rs`:

- `help_flags_are_bare_switches_and_ignore_lookalikes`
  - each of `--open-help` / `--help-window` sets `open_help` and `is_empty()`
    is false;
  - `--help`, `--open-help=1`, `--help-window=yes`, `--open_help` leave the
    struct equal to `LaunchOptions::default()`;
  - `--light`, `--dark`, `--controls=macos`, `--panel=files`, `--tool=sign`,
    `--set-title=Plan`, `--assistant-question=Why?` each still parse when
    combined with `--open-help` (table-driven, reusing the existing flag set).
- Existing `tool_flag_parses_stable_names_and_ignores_unknown_values`,
  `launch_flags_parse_and_override_saved_settings`, and
  `assistant_question_flag_is_a_capture_only_override` are unchanged and pass.

`crates/pdfxi-app/src/ui.rs`:

- `help_window_opens_through_the_launch_flag` (see above). The pre-existing
  `help_window_opens_through_a_command` still covers the menu path.

No API mismatch: `PdfxiApp::help_open()` already exposed the field, so no new
accessor was needed and the test lives inside the `ui` tests module where the
private `apply_launch_help` is visible.
