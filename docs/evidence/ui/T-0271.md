## What shipped

### A-13 - blank-page insert

`crates/pdfxi-app/src/shell/organize_card.rs` now owns
`const BLANK_PAGE_PDF: &[u8]`, a self-written one-page US-Letter PDF:

- 612x792 `/MediaBox`, `/Type /Page`, empty `/Resources << >>` and an empty
  `/Contents` stream with `/Length 0`;
- a correct xref table (`startxref 267`, objects at offsets 9, 58, 115 and 219);
- no font, text, image or Adobe asset.

`pdfxi_core::pages::PageOperation` still has no insert variant. Insertion is
composed from the existing planner: the document is split with
`PagePlan::extract` into the pages before and after the insertion point, and the
blank document is merged back in with `PagePlan::merge`. The intermediate and
final bytes are reparsed with `Document::from_bytes`; a template or planner
failure returns the typed `PageInsertError` string and never panics.

The commit path is exactly the one already used by the Organize card:
`DocumentSession::edit_full` followed by `after_session_edit`. A page-plan
rewrite (fresh object numbers) is not an incremental append, so `edit_full` is
the documented boundary; undo does not cross the insertion.

`AppCommand::AddPage` calls `handle_add_page_command`: it inserts after the
active page, updates the tab's page count explicitly, selects the new blank page
and sets `Inserted a blank page after page N`. With no document it sets
`Open a document to add a page` and opens nothing.

The Organize Pages card also gained real **Insert blank page before** and
**Insert blank page after** buttons. The old shipped copy saying insertion was
unavailable is gone.

### A-26 - page menu

`AppCommand::PageMenu` calls `handle_page_menu_command`, which opens/closes the
small **Page** window (an `egui::Window` next to the Pages panel) and reports
`Page menu: choose a page action` or `Page menu closed`. With no document it
reports `Open a document to manage pages`.

Every entry performs a document action through `run_page_menu_action`; none only
sets status:

| Entry | Effect |
| --- | --- |
| Insert blank page before | `insert_blank_page_at(current)` |
| Insert blank page after | `insert_blank_page_at(current + 1)` |
| Rotate left | one counterclockwise quarter turn on the current page |
| Rotate right | one clockwise quarter turn on the current page |
| Delete page | remove the current page, refusing the last page |
| Extract page | write `<stem>-page-N.pdf` beside the source and open it |

All document mutations use the same `edit_full` + `after_session_edit` path as
the Organize card.

## Blank-page template rationale

The shell must not invent page dictionaries in code, so the template is a
literal, minimal PDF that the library parser validates on every use. It was
checked independently with the workbench CLI:

```text
target/debug/pdfxi.exe info target/tmp/c-len0.pdf
file: target/tmp/c-len0.pdf
pdf_version: 1.4
bytes: 430
pages: 1

target/debug/pdfxi.exe text target/tmp/c-len0.pdf
<no output, exit 0>
```

The bytes are not written on their own; they exist only as a source document for
`PagePlan::merge`. A malformed template would therefore fail the click with a
typed message instead of shipping a corrupt page.

## Limits

- AddPage inserts a US-Letter blank page; it does not copy the current page's
  size or rotation.
- The page menu is a conventional floating window, not anchored to the Pages
  button. Its entries act on the current page (or the active page); the Organize
  card acts on its multi-selection.
- Extract writes beside the source document by default (documented behavior of
  the Organize card) and opens the result in a new tab; there is no save dialog.
- Page-plan commits are full rewrites, so undo does not cross an insertion,
  rotation or deletion.
- No capture is claimed; `T-0262` owns installed-build captures.

## API notes / mismatches

- The brief's stated head/tail ranges (`0..i` and `i..n`) insert *before* the
  active page, while its requested status (`Inserted a blank page after page N`),
  its requested new current page (`i + 1`) and the test description describe
  inserting *after* it. `AddPage` therefore uses insertion point
  `current + 1` with the same `extract` + `merge` composition; the generic
  `insert_blank_page_at(index)` supports both directions, and the page menu uses
  it for before/after.
- `PdfxiApp::open_document` returns `state::OpenOutcome`, not `bool`; the test
  helper asserts the resulting page count instead.
- `pdfxi_core::Document::from_bytes` takes `Vec<u8>` and `apply_page_plan`
  returns `Vec<u8>`; `PagePlan::extract` rejects an empty selection, so the
  insertion helper never calls it with an empty range.
- Tooling mismatch: the lane-app agent permission allows `docs/evidence/app/**`
  but not `docs/evidence/ui/**`, so this file was written with the permitted
  shell tool rather than the edit tool. The task's `owns` list and the campaign
  convention point at `docs/evidence/ui/`.
