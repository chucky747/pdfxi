# T-0245 - Certificate signing shell (Round B)

Status: verified for the A-20 (certificate signing and badge), A-25 (Fill & Sign
signature placement) and A-31 (signature request and local tracker) acceptance
slice; SEC-006 stays with T-0267. No feature-matrix row is promoted (promotion
is reviewed at T-0262) and no capture is claimed for the A-25 or A-31 cards.

Claim: app lane, `crates/pdfxi-app/src/**`, this file and
`orchestration/feature-updates/T-0245.toml`. Target directory
`target/lanes/app9`, features `ui,pdfium`.

## Entry points

`Capability::Signing` is enabled in `Capabilities::available()`, so the same
`AppCommand::Sign` (`label = "sign"`) is reachable from all three places a
signature starts:

- the command-bar feature button `Sign` (`command_bar_features`),
- the Tools panel row `Sign` (`tool_rows`), and
- the `--tool=sign` launch deep link, which dispatches the same command.

`AppCommand::Sign` calls `PdfxiApp::handle_sign_command`: closed, it opens the
card; open, it runs the signing flow. The card's own Sign button dispatches the
same command, so the keyboard path and the button path are identical.

The card requires an active document and refuses read-only tabs. With no
document the status line says `Open a document before signing`; with signing
disabled it says so, and no window opens.

## Sign card

`egui::Window::new("Sign")` in `crates/pdfxi-app/src/shell/signing.rs`:

- **Identity**: Choose PFX..., native picker filtered to `.pfx`/`.p12`, masked
  password, Load identity, signer subject, certificate-chain length.
- **Signature options**: reason, location, page (1-based drag value clamped to
  the page count), appearance text.
- **Actions**: Sign (enabled only with an imported identity, an active writable
  tab, and no worker) and Close.
- **Verification**: status, signer, SHA-256 fingerprint, signing time,
  whole-file coverage, appended-after-signature, chain trust, and an inline
  E-signed line when the badge predicate holds.

Every editable field is a real value used by the signing call. Blank reason and
location fall back to `Digitally signed` and `PDFXI` because `SignOptions` wants
non-empty values.

## PKCS#12 import

`load_signing_identity` reads the chosen path with `std::fs::read` and calls
`pdfxi_security::SigningIdentity::from_pfx(&bytes, &password)`. On success it
stores `subject = signer_subject()` and `chain_len = chain_len()`, keeps the
identity in memory only (`SigningUiState::identity`), clears the typed password
immediately, clears the identity error, and reports
`Sign: identity loaded (N certificate(s))`. On failure it clears the identity
and subject, keeps the password for a retry, and shows the typed
`SecurityError` string (bad password, malformed PFX, unsupported algorithm,
missing key or certificate). The private key never leaves the `SigningIdentity`
value and is never written to disk or persisted in settings.

## Typed appearance and revisions

Signing adds a visible `/Text` note on `self.signing.page` through
`pdfxi_edit::add_text_note`, at the bottom-right of the page media box (right
edge minus 60 pt, 36 pt up), 24 pt square, contents = the appearance text,
author = the local display name, `/NM = pdfxi-signature-N`.

`SessionError` has no `AnnotationEditError` variant and the edit crate does not
convert into it, so the appearance uses the same pattern as `comments.rs`:
clone `session.document()`, run the library on the clone, then commit with
`session.edit(|document| { *document = candidate; Ok(()) })`. That is one
incremental revision.

`DocumentSession::sign(&identity, &SignOptions { page_index, field_name:
"Signature-N", reason, location, ..Default })` then appends the certificate
signature as a second incremental revision. **Decision: two revisions.** The
signature revision covers the appearance revision's bytes, so the visible note
is inside the signed byte range; the session API has no single call that adds an
annotation and signs in one revision. The session is dirty afterwards and
`after_session_edit` refreshes the dirty marker, canvas, annotations and forms.

## Verification readout

After signing, the card calls `pdfxi_security::verify_signature(session.bytes())`
and stores the result for the signing tab. The panel shows, unchanged:

- status (`Valid`, `Tampered`, `Invalid`, ...),
- signer subject,
- lowercase SHA-256 certificate fingerprint,
- asserted signing time in UTC,
- `Covers entire file`,
- `Appended after signature`,
- `Certificate chain`, where `None` is shown as **identity not verified**, not
  as trusted.

A verify-only failure after a successful sign is stored in `verification_error`
and shown separately; the signature field sequence is kept because the
signature is in the document.

## Badge rule and on-page chip

`badge_visible_for` is exactly

```text
status == Valid && bytes_match && covers_entire_file && !appended_after_signature
```

`signature_badge_visible` adds the tab guards (below) and is the only condition
that draws the green rounded **E-signed** label above the typed note, using the
same `page_rect_to_canvas` page-to-screen transform as the annotation and find
overlays (`document_view.rs` calls `signature_badge_ui` each frame). The chip is
a label, not a control, and disappears as soon as the predicate fails. The same
predicate gates the inline E-signed line in the panel.

The visible block is an app overlay, not PDF content. `signature_badge_ui`
draws a 220x56 pt rounded surface at the bottom-right of the signing page with
a 1 px border, the signed appearance text, the certificate signer subject and
the asserted signing time, clipped to the page with the same transform as the
find highlights. The 96x18 pt green `E-signed` chip sits directly above it.
Opening a signed document scrolls the page so the block is in view. The
appearance text is read back from the document's `pdfxi-signature-` `/Text`
note on open; when no note exists it falls back to
`Digitally signed by <signer subject>`, never the local display name. The
`/Text` annotation and the certificate signature in the PDF are unchanged.

## Per-tab scoping

A readout belongs to one tab and one byte state:

- `signature_badge_visible` requires both `self.signing.tab` and
  `self.signing.verification_tab` to equal the active tab, so a card reopened on
  another tab cannot inherit the previous result.
- `signature_verification_ui` shows `Not checked for this document` instead of
  another tab's signer/fingerprint when the readout's tab is not active.
- `after_session_edit` clears the verification result, so any edit, undo or redo
  drops the badge until the bytes are checked again.

## Verification on open

`open_document_session` calls `verify_signature_on_open(id)` once, immediately
after the new session is inserted and `finish_new_tab` runs, before the dirty
sync. The function:

- `Ok(verification)`: stores the result, `verification_tab = Some(id)`,
  `signing.tab = Some(id)`;
- `Err(SecurityError::SignatureNotFound)`: clears result, tab and error, so an
  unsigned document shows nothing and no error;
- any other error (malformed `/ByteRange`, DER/CMS, unsupported algorithm):
  stores `verification_error` for that tab and no result.

Password retries go through the same function, so a password-protected signed
PDF verifies on the successful retry. An already-open tab takes the `Focused`
branch and is not re-verified. Nothing verifies per frame. `--tool=sign` on a
signed file therefore shows the chip and the verification lines immediately,
without loading an identity or signing again.

## Field-name seeding

`SigningUiState::signatures` starts at zero each run, so before signing
`next_signature_sequence(id)` reads `pdfxi_forms::read_acroform` on the session
document, collects every `FormFieldKind::Signature` name, and returns the first
free `Signature-N` at or above the run counter. A damaged AcroForm falls back to
the run counter and lets the library's own error surface. The ignored test signs
a fixture, reopens the bytes and asserts the existing `Signature-1` yields
`Signature-2`.

## A-25 signature placement

This is Fill & Sign placement, not a certificate signature. The *Place
signature* card in `crates/pdfxi-app/src/shell/signature_place.rs` places a
visible mark on the active page; it never loads a PKCS#12 identity, never calls
`DocumentSession::sign`, and never touches the verification readout or the
E-signed badge. The *Sign* card in `signing.rs` (A-20, above) remains the only
cryptographic path. The two cards keep separate state (`signature_place` and
`signing` in `PdfxiApp`) and separate commands (`place-signature` and `sign`).
The Fill & Sign panel in `forms.rs` fills AcroForm fields; this card adds a
visible mark and works whether or not the document has a form.

### Entry and gating

`AppCommand::PlaceSignature` (`label = "place-signature"`) dispatches
`handle_place_signature_command`: closed, it opens the card for the active tab;
open, it places with the selected mode. The card belongs to the Fill & Sign
acceptance item (A-25); it is not the certificate Sign card.

- `Capability::Signing` is required; without it the status says
  `Signature placement is not enabled in this build` and no window opens.
- An active document is required (`Open a document before placing a
  signature`) and a read-only tab is refused (`The document permissions do not
  allow changes`).
- Opening resets the mode to Type, clears the drawn points, the image path and
  the error, and prefills the typed name from `settings.display_name`.
- `place_signature_dialog_ui` runs every frame from `ui.rs::update`; the card
  closes after a successful placement or from its own close button.

### Modes

All three modes target the same rectangle on the active page: 220x56 pt, inset
36 pt from the media box right and bottom edges (`x0 = right - 36 - 220`,
clamped to `left` on a narrow page; `y0 = bottom + 36`). Placement never uses
the pointer position on the page.

- **Type**: `pdfxi_edit::add_stamp` with the standard `/Name Approved`, the
  trimmed typed name as the appearance label and `/Contents`, and the local
  display name as author. The Place button is disabled while the field is
  blank; `add_stamp` caps the text at 200 characters.
- **Draw**: a 260x80 pt `egui` pad with `Sense::drag()`. Pointer positions are
  stored normalized to 0..1 (clamped), with a 0.002 movement threshold, and the
  preview is redrawn as a 1.5 pt line. On place, the normalized points are
  mapped into the same 220x56 rect and submitted as one stroke through
  `pdfxi_edit::add_ink(..., 1.5, "Signature", author)`. At least two points are
  required.
- **Image**: a native `rfd` picker filtered to `.png`, `.jpg` and `.jpeg`. On
  place the file is read and the format is detected from the magic bytes
  (`89 50 4E 47` for PNG, `FF D8` for JPEG); anything else is rejected with
  `Choose a PNG or JPEG image`. `pdfxi_edit::add_image` (in
  `content_edit`) places the image at the same rect.

### Commit path

Every mode runs the same three steps:

1. `placement_target` checks the card's tab is still active and writable, reads
   the page media box, computes the rect and clones `session.document()`.
2. The library call mutates the clone; a rejected input leaves the session
   untouched and the error stays in the card.
3. `commit_placement` commits the clone with
   `session.edit(|document| { *document = candidate; Ok(()) })` and then calls
   `after_session_edit(id)`.

That is one incremental revision, so the placement is undoable. The post-edit
hook refreshes the dirty marker, canvas and rasters, thumbnails, annotations
and forms, and clears the signature verification readout. On success the card
closes and the status says `Placed typed signature on page N` (or drawn/image).

### Limits

- Fixed bottom-right placement. There is no drag-to-place, no free position and
  no move or resize after placing; the way to change a placement is undo and
  place again.
- Placement is on the active page only; there is no multi-page or all-pages
  placement.
- Image mode accepts PNG and JPEG only and trusts the magic bytes; `add_image`
  ignores the PNG alpha channel (round A library behavior), so a transparent
  signature is flattened, and the image becomes page content, not an
  annotation, so it does not appear in the annotation list.
- Drawn mode is a single stroke and reads back as `AnnotationKind::Pencil`
  (`/Ink`), not a dedicated signature kind.
- Typed mode always uses `/Name Approved`; non-ASCII characters are rendered
  as `?` in the appearance while `/Contents` keeps the exact typed text.
- Entry in this tree: the Tools panel row `Place signature` opens the card when
  `Capability::Signing` is enabled and a document is open; there is no
  `--tool=place-signature` deep link and no Fill & Sign panel control for it.

## A-31 request and tracker

The lower half of the Sign card composes a signature request in the user's own
mail client and tracks it in a local list. PDFXI never sends mail itself and
never contacts a service.

### Request panel

`signing_dialog_ui` in `crates/pdfxi-app/src/shell/signing.rs` draws, below the
signing actions and separated by a rule:

- the **Request signature** heading;
- **Recipient email** (`request_recipient`), a single-line field;
- **Subject (optional)** (`request_subject`), a single-line field;
- **Message (optional)** (`request_message`), a two-row multiline field; and
- **Send request**, enabled only while the recipient field contains `@`.

Blank subject and message fall back to `Signature requested: <document name>`
and `Please sign <document name> and return the signed copy as a reply.`; the
body adds `Document: <name>` and the instruction to reply with the signed PDF
attached. Every typed value is used by the send call; nothing is stored in
settings.

### Send path

`send_signature_request` calls `send_signature_request_with(open_mailto)`; the
launcher is a parameter so tests never start a process. The order is:

1. An active tab is required (`Open a document before requesting a signature`).
2. The session must have a path on disk, so a request always names a saved file
   (`Save the document before requesting a signature`).
3. The recipient is trimmed, must be non-empty and must contain `@`
   (`Type the recipient's email address`).
4. `request_mailto_url` builds
   `mailto:<recipient>?subject=<percent-encoded>&body=<percent-encoded>`. The
   recipient is inserted as typed so its `@` stays readable; space, `@`, `&`,
   `=`, `#`, `?` and line breaks in the subject and body are percent-encoded.
5. `open_mailto` hands the URL to the platform (`cmd /C start` on Windows,
   `open` on macOS, `xdg-open` elsewhere). It is the only process launch in the
   flow and it does not wait for the mail client.
6. Only after the launcher succeeds is a **pending** row recorded and the
   tracker saved. A launch failure records nothing, writes no file, and reports
   `Could not open the mail client: ...` in the card. A tracker write failure
   reports `Could not save the signature requests: ...`.

A successful send clears the message field and sets the status to
`Signature request recorded for <recipient>`.

### Tracker file

The list is one tab-separated file per user, resolved at runtime:

- Windows: `%APPDATA%\PDFXI\sign-requests.tsv`, falling back to the roaming
  profile under the home directory;
- other systems: `$XDG_CONFIG_HOME/PDFXI/sign-requests.tsv`, falling back to
  `~/.config/PDFXI/sign-requests.tsv`;
- last resort: the OS temporary directory.

A row is `id`, absolute document path, recipient, subject, Unix send time and
`pending` or `signed`. `SignRequestTracker` escapes backslashes, tabs and line
breaks inside a field, writes the header line before every row, recreates the
parent directory on save, and assigns each request the previous maximum id plus
one. `load_sign_request_tracker` loads the file once when the card opens and
keeps the path in `signing.tracker_path`; a missing, unreadable or corrupt file
loads as an empty list, and a corrupt row is skipped rather than failing the
open or panicking.

### Tracked requests list

The same card draws a **Tracked requests** heading under the send controls:

- `No requests yet.` when the list is empty,
- `N awaiting a signed copy` while any request is pending, and
- one line per request in insertion order,
  `<recipient> - <document file name> - <pending|signed>`.

### Returned signed copy

`open_document` runs `verify_signature_on_open` once and then, when the opened
file verified with a signer subject, calls
`mark_returned_signature(path, Some(signer_subject))`. `mark_signed_for` marks
every matching `pending` row `signed` when either

- the row's document path equals the opened path, or
- the recipient text appears case-insensitively in the signer subject (for
  example `ada@example.com` in `CN=Ada Lovelace, E=ada@example.com`).

A change is saved back to the tracker file and the status says
`A returned signature was matched to a request`. No match leaves the list
untouched; an unsigned or unverifiable copy never marks anything, and the match
runs on open only, not per frame.

### Deep link

`AppCommand::RequestSignature` (`label = "request-signature"`) is dispatched by
`--tool=request-signature` (and the `request-sign` alias). The command opens the
Sign card for the active document and says
`Signature request: type the recipient`; if the card is already open it only
repeats `Signature request: type the recipient, then Send request`. Navigation
never sends, because sending is the card's explicit Send request button. The
Tools panel hides the row while no document is open.

### Limits

- No network call by PDFXI. The request is a `mailto:` compose window handed to
  the default mail client; PDFXI sends no SMTP or API request, attaches no file,
  and has no Simple MAPI integration, so the campaign note's
  MAPI/attachment-fallback wording is not what this slice implements.
- No delivery or read receipt and no open tracking. The card cannot tell
  whether the mail client actually sent the draft, and a closed compose window
  still leaves a pending row.
- No recipient identity check. The signer-subject match is a case-insensitive
  substring test on the certificate subject, and the path match is on the local
  absolute path, so a renamed or relocated returned copy matches only by signer
  subject.
- A request needs a saved document: an unsaved document is refused with
  `Save the document before requesting a signature`.
- A matched row means "matched", not "trusted". There is still no certificate
  trust anchor until T-0267, so `signed` does not claim the signer's identity.
- The tracker is a flat file with no expiry, deduplication, delete-row action or
  cross-machine sync.

## Current limits

- **A-25 limits**: the Place signature card always lands at the bottom-right of
  the active page. There is no drag-to-place, no free position, no move or
  resize after placing, and no multi-page placement. Image mode flattens PNG
  alpha and becomes page content rather than an annotation; drawn mode is one
  stroke read back as `AnnotationKind::Pencil`. The Tools panel offers a
  "Place signature" row gated on `Capability::Signing` plus an open document,
  so the card is reachable from the shipped GUI (`capabilities.rs`,
  `tools_panel.rs`, proved by
  `place_signature_tool_row_appears_with_a_document_and_opens_the_card`);
  there is no `--tool=place-signature` deep link.
- The certificate signature's appearance is still a typed `/Text` note inside
  the PDF plus an app-overlay block and chip, not a drawn or image stamp.
- **A-31 limits**: PDFXI makes no network call; sending only hands a `mailto:`
  URL to the platform mail client, so there is no delivery or read receipt and
  no recipient identity check. Tracker matching is local: the row's saved path
  equals the opened path, or the recipient text appears in the verified signer
  subject. The document must be saved before a request, and chain trust stays
  `None` until T-0267.
- Verification runs on document open and is cleared by `after_session_edit`; it
  is not re-run after a save, and there is no persistent multi-signature list or
  badge for non-active tabs.
- Chain trust is always `None` in the readout until T-0267 wires trust anchors,
  timestamps and revocation; the panel says `identity not verified` rather than
  implying a trusted signer.
- Encrypted documents refuse signing (`EncryptedSignUnsupported`), and the PFX
  read and signing call are synchronous on the UI thread (measured ~0.1 s for
  the fixture); no progress window or Stop control is shown.
- SEC-005/FORMS-010 are not promoted here: A-20, the A-25 placement and A-31
  are UI-complete, but the final matrix promotion is reviewed at T-0262, and
  SEC-006 belongs to T-0267.
