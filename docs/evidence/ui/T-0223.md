# T-0223 Round A - printing through the Windows print dialog

Date: 2026-11-20. Lane: app. Status: review (Round A complete; manual real-
printer verification and booklet/N-up remain).

The viewer prints real documents through the Windows GDI path. The document's
session bytes are rasterized by PDFium at the printer's own DPI, converted to a
top-down 32-bit DIB, and sent to the device context selected in the native print
dialog. No file must be saved first, so unsaved edits print as shown.

## Backend calls used

Declared directly with `#[link]` in `pdfxi_render::win_print` (the workspace
already links these system DLLs):

- `comdlg32`: `PrintDlgW`, `CommDlgExtendedError`, `GlobalFree` for the returned
  DEVMODE/DEVNAMES blocks.
- `gdi32`: `CreateDCW` (print-to-file route), `GetDeviceCaps` (`LOGPIXELSX`,
  `LOGPIXELSY`, `HORZRES`, `VERTRES`), `StartDocW`, `StartPage`,
  `SetStretchBltMode(HALFTONE)`, `StretchDIBits` (32 bpp BGRA, negative height
  for top-down, `SRCCOPY`), `EndPage`, `EndDoc`, `AbortDoc`, `DeleteDC`.
- `kernel32`: `GetLastError`.

The native dialog supplies printer, paper, page range and copies. The
pre-print panel supplies fit/actual size and orientation, which the dialog does
not expose consistently across drivers. Page range is resolved from the
dialog's `PD_ALLPAGES`/`PD_PAGENUMS`/`PD_CURRENTPAGE` flags, clamped to the
document, with reversed bounds swapped.

Every path frees the DC, DEVMODE and DEVNAMES; a cancelled job calls
`AbortDoc`; a render or page error also aborts before returning.

## Page and DPI math

For a page of `w_pt x h_pt` and printer metrics from `GetDeviceCaps`:

- base pixels = `w_pt / 72 * dpi_x`, `h_pt / 72 * dpi_y`;
- `Fit`: factor = `min(printable_w / base_w, printable_h / base_h)`;
- `Actual`: factor = 1; `CustomPercent(p)`: factor = `p / 100`;
- destination size = rounded base size times the factor, clamped to the
  printable area for Fit, centered with `(printable - dest) / 2`;
- renderer scale = `dest_width / page_width_pt` (1.0 = 72 DPI);
- Landscape rotates a portrait page 90 degrees clockwise before drawing and
  swaps the fitted dimensions.

The page is measured by rendering once at scale 1.0 (one pixel per point)
because the `Renderer` trait's page-size method is optional; the final raster is
then rendered at the printer-DPI scale. The print-to-PDF output confirms the
physical size: 3600 x 4659 device pixels at the driver's printable-area DPI.

## Automated print test - what it proved

`print::backend_tests::prints_first_page_through_microsoft_print_to_pdf` prints
page 1 of `fixtures/realworld/microsoft-excel-2019-sample.pdf` with
`print_to_file`, `DOCINFO.lpszOutput = target/lanes/app/t0223-out/printed.pdf`,
and the "Microsoft Print to PDF" driver. It then reopens the file through
`DocumentSession`.

Observed output:

- `target/lanes/app/t0223-out/printed.pdf`, 352876 bytes;
- `DocumentSession` page count: **1**;
- the printed PDF contains one page object and one `/Subtype /Image` XObject
  (3600 x 4659, DCTDecode); it contains **no fonts and no text objects**;
- rendering the printed page at scale 0.5 produces real ink (the assertion is
  `ink > 1000` non-white pixels).

The task text asked to assert "the page text". That is not possible on this
path: GDI printing rasterizes the page, so the Print to PDF driver writes an
image, not selectable text. The test asserts the honest equivalent - exactly one
page, the selected page's image, and non-blank ink after rasterization - rather
than faking a text match.

## Safety and module placement

`crates/pdfxi-app` keeps `#![forbid(unsafe_code)]`. Win32 FFI requires `unsafe`,
so the backend lives in the new `crates/pdfxi-render/src/win_print.rs`. The
render crate's crate-level lint changes from `forbid` to `deny` and that one
module opts in with `#![allow(unsafe_code)]`; every other module stays
`deny`. `crates/pdfxi-app/src/print.rs` re-exports the backend so the shell has
one import.

## Review note: crate-level unsafe invariant changed

Reviewed with the accepted round. `crates/pdfxi-render` moved from
`#![forbid(unsafe_code)]` to `#![deny(unsafe_code)]` in `src/lib.rs`, and only
`src/win_print.rs` overrides it with a module-level `#![allow(unsafe_code)]`.

Why: the Windows device adapter needs Win32 GDI and the native print-dialog FFI.
There is no safe standard-library equivalent for `StartDoc`/`StartPage`/
`StretchDIBits`, `DOCINFO`, `DEVMODE` and the `PrintDlgW` ownership rules, and
wrapping the whole crate would have hidden the boundary. Every other module
remains denied: `deny` rather than `forbid` is what makes the single documented
exception possible, and it is the only `allow(unsafe_code)` in the crate
(`win_print.rs` line 15, next to the module docs stating the invariant).

Risk: `deny` can be overridden by any future module in this crate, and `forbid`
cannot. The exception is currently one file and one dependency-free OS API
surface, so the blast radius is inspectable.

Proposed follow-up: move the GDI/print-dialog FFI into its own crate
(`crates/pdfxi-print-win`, `#![forbid(unsafe_code)]` everywhere else in
`pdfxi-render`), with a safe trait implemented by that crate and gated by the
same `pdfium`/platform feature. Then `pdfxi-render` returns to
`#![forbid(unsafe_code)]` and the unsafe boundary is a crate boundary instead of
a module convention. Not done in T-0223; recorded for wave C.
