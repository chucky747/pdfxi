| Control | Behaviour | Where |
|---|---|---|

| Checkbox widget on the page | Drawn at its real `/Rect`; clicking toggles it through the session. The checked state is a vector check mark in the box, not a filled block, so it matches the PDF's own checked appearance. | `form_checkbox_widget_ui` |
| Choice / radio / button / signature | Drawn read-only at their real rectangles with their current value in muted ink. Deliberately **not** interactive in round A: an unwired control would be a dead control. | `form_widgets_ui` |
| Panel field list | Name, kind and current display value for every field, a hint line, and a banner for a read error or an XFA/JavaScript notice. | `forms_panel_ui` |
| Undo / redo | Each commit is one `DocumentSession::edit`, so Undo/Redo restore values and widgets. `after_session_edit` -- the single post-edit hook already used by open, undo and redo -- now also calls `refresh_forms()`, so the panel and widgets cannot show a stale value after an undo or redo. | `shell/session.rs`, `shell/forms.rs` |

## 2. Model, caching and errors

- On open, tab switch, undo/redo and every form edit the shell calls
  `pdfxi_forms::read_acroform(session.document())` and caches the
  `AcroFormModel` **keyed by the tab and `DocumentSession::revision_count()`**;
  an unchanged revision does no work.
- Values are committed with `pdfxi_forms::set_text` / `set_checkbox` on a clone
  of the session document, then committed as one `session.edit` -- the same
  clone-then-commit shape T-0242 uses for annotations. The library writes `/V`,
  widget `/AS` and regenerates `/AP /N`; the shell never parses or writes a field
  dictionary and never changes library semantics.
- The library documents that `read_acroform` returns the snapshot it was called
  with, so after a commit the cached model is also updated with the value that
  was actually written. A later revision (undo, tab switch, save/reopen) replaces
  it from bytes.
- Typed failures are surfaced, never swallowed: a malformed AcroForm shows the
  `AcroFormError` message in the panel banner; an unknown, read-only or
  wrong-kind field refuses with one sentence and appends no revision; `/XFA` and
  JavaScript actions produce a notice that they are **not** rendered or
  executed. No XFA and no script is ever run.

## 3. Read-only and permission gate

`form_edit_blocker(read_only, fill_allowed)` is a pure, unit-tested gate:

- the tab is read-only (an encrypted document whose permissions deny `MODIFY`), or
- the document `/Perms` mask denies `FILL_IN_FORM` (`Permission::FILL_FORMS`).

Either refusal paints the widgets without interaction, writes a short hint in the
panel and status line, and leaves the tab clean (no session revision).
Field-level `/Ff` read-only is refused by the library
(`AcroFormError::ReadOnlyField`) and is also checked against the cached model
before the edit, so nothing is appended.

## 4. Save, reopen and appearance proof

`save_active_as` writes the session bytes: `/V` for every filled field, the
widget `/AS`, and the regenerated appearance streams. The artifact
`target/lanes/app2/t0243-out/filled.pdf` (identical copy:
`filled-form.pdf`, the file the capture script opens) is written by the test and
reopened by a **fresh** `PdfxiApp`: three fields, `text-field` =
`Reviewed 2026-11-20`, `checkbox-field` = `On`, `choice-field` = `two`.

Independent proof: the saved bytes are rendered by PDFium at scale 2 and the
pixels inside the text widget rectangle `[72 700 272 720]` are counted; the test
requires real ink there, which a `/V`-only write cannot produce.

## 5. `--tool=` launch flag

`settings::LaunchOptions` gained `tool: Option<LaunchTool>` parsed from
`--tool=<name>` (case-insensitive, last one wins, unknown values ignored):
`edit`, `comment`, `highlight`, `fill`/`fill-sign`/`fill-and-sign`/`forms`,
`sign`, `organize`, `export`, `convert`, `protect`, `ai`/`assistant`.
`fill` maps to `LaunchTool::Fill`, which dispatches the real
`AppCommand::FillAndSign` after the startup document opens -- the same command the
Tools row emits, so a deep link can never do more than the control. With the
capability off or no document, the dispatch takes the ordinary hint path: no
panic, no placeholder. `LaunchTool::as_str()` returns the stable names, which is
the shape T-0262 can use for every installed tool.

Three defects were found and fixed while capturing:

1. **Panel covered the page.** The Fill & Sign window opened centred over the
   widgets. It now defaults to the lower-left of the workspace (still movable),
   so the page and its fields are visible.
2. **Dark-mode field ink.** Widget text drew with `palette.text`, which is
   near-white in dark mode on the always-white page. Page-space widget text now
   uses a fixed dark ink (`FIELD_INK`, with a muted variant for read-only kinds)
   in every theme, including the focused `TextEdit`.
3. **Checkbox presentation.** The checked checkbox painted a red filled square
   over the real appearance; it now draws a vector check mark, so the capture
   matches the saved PDF.

Capture prerequisite: `target/lanes/app2/release/pdfium.dll` had to be copied
next to the release executable (the lane build does not package it). Without it
the viewer reports `could not load the PDFium library` and the canvas stays
blank; with it the page renders and the captures above are reproducible.
