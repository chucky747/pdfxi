# T-0190 — R1 GUI opens real PDFs; demo path resolved at runtime

Date: 2026-11-20. Lane: integrator. Target dir: `target/integration`.

## Delivered

- **Open a real PDF from the GUI.** New toolbar `Open…` button opens an in-app
  "Open PDF" dialog (typed path, Enter or Open submits, Cancel closes) and the
  window accepts PDF files dragged from Explorer. Both paths funnel through
  `PdfxiApp::open_path_text`, which trims whitespace and surrounding quotes,
  rejects empty input, control characters, non-`.pdf` extensions and
  non-existent files with a status message before touching loader state, then
  reuses the existing duplicate-path-focusing `open_document`.
- `PdfxiApp::open_dropped(&[PathBuf]) -> usize` opens every PDF in a batch,
  ignores non-PDF drops, and keeps the specific error status when a dropped PDF
  fails to open (for example `File not found: …`) instead of masking it.
- `PdfxiApp::is_pdf_path` is a public, case-insensitive extension check.
- **No baked build path.** `raster::workspace_fixture_path` (which used
  `env!("CARGO_MANIFEST_DIR")`) is replaced by `fixture_candidates` +
  `find_fixture_in` + `demo_fixture_path`, which walk up from the running
  executable and then from the working directory (bounded to 8 ancestors per
  root, deduplicated, separator-free names only). A layout without a
  `fixtures/` directory starts cleanly with the status
  `No demo fixture in this layout; use Open… or drop a PDF` instead of an
  error.

### Dependency note

The plan named `rfd` for a native picker. `rfd` is not present in the offline
registry cache and this host has no network, and `pdfxi-app` is
`#![forbid(unsafe_code)]` so a raw Win32 dialog is not possible either. The
shipped solution is therefore dependency-free (typed-path dialog + native drag
and drop). A native picker remains a planned follow-on once the dependency can
be fetched and allowlisted.
