# T-0317 — JavaScript sandbox host (`AUTO-004`)

Row promoted: `AUTO-004` (Sandboxed Acrobat-compatible JavaScript subset)
`model` -> `verified`.

The interpreter and Acrobat context existed, but the row's own note recorded
"no CLI entry point". This task adds one.

## 1. Host

```text
pdfxi script run <SCRIPT.js> [--field NAME=VALUE ...]
    [--event-key KEY] [--event-value VALUE] [--max-steps N] [--json]
```

- Reads a real script file and enforces `MAX_SCRIPT_BYTES`.
- Seeds an in-memory `AcrobatContext`: `--field` populates
  `this.getField(name).value`, `--event-key`/`--event-value` populate `event`.
- Parses and runs through `run_acrobat_script` with the default budgets
  (100000 steps, 64 nested calls, bounded loops, strings, arrays, objects and
  AST depth) or a tighter `--max-steps`.
- Reports the return value and its JavaScript type, every final field (sorted),
  and `event.key`/`event.value`/`event.rc`. `--json` emits stable fields.
- The sandbox has no file, network, process, clock, randomness or ambient
  global access; `eval`, `Function`, `require`, `process`, `globalThis`, etc.
  are rejected by name.

## Scope

The field store is in memory: this command does not mutate a real PDF form and
does not expose the `ActionSequence`/`SequenceRunner` batch binding. It is the
raw sandbox entry point; console/file/network effects remain unavailable by
design.
