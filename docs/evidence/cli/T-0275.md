# T-0275 — Virtual PDF printer: print from any application, capture the job

## What changed

`CREATE-001` ("Create PDF from any printable application") and `CREATE-002`
("Virtual PDF printer") had a validated print-job envelope and an assembly plan
in `pdfxi-convert`, but no host path: nothing on Windows could print into PDFXI.

This task adds the missing host surface as `pdfxi printer`:

```text
pdfxi printer install [--name "PDFXI PDF"] [--port <absolute file>] [--json]
pdfxi printer status  [--name ...] [--port ...] [--json]
pdfxi printer remove  [--name ...] [--port ...]
pdfxi printer watch   [--name ...] [--port ...] --out <file> [--timeout secs]
```

- `install` creates a **local printer port whose name is a file path**
  (`%LOCALAPPDATA%\PDFXI\Inbox\capture.pdf` by default) and a queue using the
  Windows `Microsoft Print To PDF` driver. The spooler writes the generated PDF
  to that file; no save dialog appears.
- `watch` waits for one finished job — file present, `%PDF-` header, size stable
  across 600 ms — copies it to `--out`, and clears the port for the next job.
- `status` reports the queue, driver, port, and whether a job is ready.
- `remove` deletes the queue and the port.
- Everything is per-user: `install` and `remove` succeed **without elevation**
  (verified in this session, `elevated=False`).

Files: `crates/pdfxi-cli/src/printer.rs` (new, documented, four unit tests),
`crates/pdfxi-cli/src/main.rs` (subcommand),
`crates/pdfxi-cli/tests/cli.rs` (three integration tests),
`scripts/test-virtual-printer.ps1` (end-to-end run),
`docs/evidence/ui/final/virtual-printer-captured.png` (the captured job open in
the installed viewer).

## Live end-to-end run

Microsoft Word printed a document through the Windows spooler to the queue; the
`watch` command captured the finished job and the captured PDF was parsed and
rendered.

```text
ok 1 - install reports the queue installed
ok 2 - the capture port is an absolute file path
ok 3 - status sees the queue in the spooler
ok 4 - the queue uses the Windows PDF driver
ok 5 - printer watch reports the captured job
ok 6 - the captured job exists
ok 7 - the captured file parses as a PDF
ok 8 - the captured PDF has at least one page
ok 9 - the captured PDF is not empty
ok 10 - the port file is cleared for the next job
ok 11 - remove takes the queue out of the spooler
VIRTUAL PRINTER OK: 11 assertions
```

The captured file:

```text

```

Opened in the installed build (`%LOCALAPPDATA%\Programs\PDFXI\pdfxi-ui.exe`):
`docs/evidence/ui/final/virtual-printer-captured.png` shows
`captured.pdf` with Pages (1) and the printed line
"PDFXI virtual printer test document, printed from Microsoft Word." on the
canvas. The origin was a real application print, not a PDFXI-created file.

Reproduce with:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-virtual-printer.ps1
```

## Honest scope

- The queue uses the inbox Windows PDF driver. PDFXI does not ship or sign a
  printer driver, so no kernel component and no elevation are involved.
- One queue writes to one port file at a time; the spooler serialises jobs, and
  `watch` clears the file between jobs. Two simultaneous consumers of the same
  queue would race; that is documented rather than hidden.
- "Any printable application" means applications that print through the Windows
  spooler. Applications that only export PDFs directly (no print path) are not
  captured, which is the normal limit of a virtual printer.
- The capture file location is per-user and portable; `--port` accepts any
  absolute path, and a relative path is rejected.
