# T-0349 — Authenticated security-envelope host (`SEC-010`)

Row promoted: `SEC-010` (Security envelopes and attachment encryption)
`model` -> `verified`.

`pdfxi_security::security_envelope` already built and opened version-1
integrity envelopes and version-2 HMAC-authenticated envelopes, but no caller
could seal or open a file. This task adds `pdfxi envelope`.

## 1. Host

```text
pdfxi envelope seal INPUT --out ENVELOPE --recipient LABEL[:PERM,PERM] ...
    [--permissions LIST] [--key-file PATH | --key-hex HEX] [--json]
pdfxi envelope open ENVELOPE --out FILE [key options]
    [--recipient LABEL --require PERM] [--json]
pdfxi envelope verify ENVELOPE [key options]
    [--recipient LABEL --require PERM] [--json]
```

- `seal` reads any payload file, builds a v2 authenticated envelope when a key
  is supplied (HMAC-SHA256 over the canonical body, plus the unkeyed SHA-256
  digest) or a v1 integrity envelope without one, and writes the container.
  Recipients are `LABEL` (envelope permissions) or `LABEL:PERM,PERM`; the
  envelope-wide mask comes from `--permissions` (`all`, `none`, `read-only` or a
  comma list of `print`, `modify`, `copy`, `annotate`, `fill`,
  `accessibility`, `assemble`, `print-high`).
- `open` verifies both tags, writes the payload and reports version, integrity,
  payload length, recipients and permissions. `verify` does the same without
  writing.
- `--recipient LABEL --require PERM` checks the recipient's declared permission
  and fails when the label is absent or the permission is not granted.
- An authenticated envelope is never accepted without the key, and an unkeyed
  envelope is never accepted with one. Keys are read from a file or hex and are
  never printed or logged. With no key, the command prints an explicit warning
  that the payload and permissions are **unauthenticated**.

```text
    --recipient "alice:print,modify" --recipient "bob:print" --key-hex 0011...eeff

```

Rejections:

```text
> verify ... --recipient bob --require modify
Error: recipient "bob" is not granted the modify permission

> verify ... --recipient carol --require print
Error: recipient "carol" is not addressed by this envelope

> verify ... --key-hex <wrong 32-byte key>
Error: open ...: security envelope keyed authentication tag did not match

> verify <authenticated envelope>            (no key)
Error: open ...: security envelope authentication requires a key and an authenticated envelope

> verify <unkeyed envelope> --key-hex ...     (key supplied)
Error: open ...: security envelope authentication requires a key and an authenticated envelope

> verify <flipped byte inside the container>
Error: open ...: security envelope integrity tag did not match its contents

> seal INPUT --out ... <no recipient>
Error: supply at least one --recipient LABEL
```

## 3. Tests

```text
> cargo test -p pdfxi-cli envelope_
envelope_authenticated_round_trip_and_authorization ... ok
envelope_unkeyed_mode_and_bad_inputs ... ok
test result: ok. 2 passed
```

The first seals a real PDF for two recipients with distinct permissions, checks
the JSON shape and byte counts, opens it byte-for-byte, verifies it, rejects a
wrong key and a missing key, allows `alice` to print, denies `bob` modify,
rejects an unknown recipient and rejects a half-specified authorization. The
second covers unkeyed sealing/opening with the warning, rejects opening an
unkeyed envelope with a key, rejects a tampered container, and covers missing
recipients, conflicting key options, an empty payload and an empty label.

## Scope

Authenticated integrity envelopes: recipients, declared permissions, SHA-256
integrity and keyed HMAC-SHA256 authentication. The payload is stored verbatim,
so this provides **no confidentiality**. Certificate-addressed encryption
(`CertificateEnvelope`/`EncryptionScope` over attachments) remains a model and
key-wrap-provider boundary; it needs a caller-supplied key-wrap backend and is
not exposed by this command. Declared permissions are an authenticated statement,
not an enforcement mechanism against a modified reader.
