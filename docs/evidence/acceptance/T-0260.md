## 1. Method

A docs-only instrument (`T-0260-scenario.rs` plus a two-file runner) compiles
against the lane's release rlibs and calls the same library functions the shell
calls, in the shell's own commit pattern: clone the parsed `Document`, run the
library mutation on the clone, commit with `DocumentSession::edit(|d| *d =
candidate)`, then `save` and reopen. That pattern is the app's
`commit_annotation` (`crates/pdfxi-app/src/shell/comments.rs:545`),
`commit_edit` (`.../edit_tool.rs:752`) and `set_form_text`
(`.../forms.rs:547-577`).

| Step | Shipping call in this run | App call site it mirrors |
|---|---|---|
| open | `DocumentSession::open`, `Document::from_bytes` | session open path |
| edit text | `pdfxi_edit::content_edit::replace_object(.., ObjectReplacement::Text)` | `shell/edit_tool.rs:422` |
| highlight | `pdfxi_edit::document_annotations::add_highlight` | `shell/comments.rs:396` |
| comment thread | `add_text_note` + `reply_to` | `shell/comments.rs:438`, `shell/commands.rs:722` |
| fill form | `pdfxi_forms::document_form::import_xfdf` | `shell/forms.rs:1097` (`import_xfdf_at`) |
| sign | `DocumentSession::sign` + `verify_signature` | `shell/signing.rs:776` |
| export to Word | `pdfxi_convert::pdf_export::export_pdf(.., ExportFormat::Docx, ..)` | `shell/export_card.rs:261` |
| reopen in PDFium | `pdfxi_render::pdfium_backend::PdfiumRenderer::from_bytes` | renderer backend |

Fixtures are opened read-only. Every output is written under
`target/tmp/t0260/` (signed PDF 214,603 bytes, `.docx` 7,921 bytes, working
copies). Nothing under `fixtures/` was modified.

## 4. What each result proves

- **Open.** The committed 3-page PowerPoint PDF parses to the same page count and
  text length (208 characters) through the session and through
  `Document::from_bytes`, so the session wrapper adds no divergence.
- **Edit text.** Page 1 has three text blocks (`text:0` preview "Lantern Slide").
  `replace_object(.., ObjectReplacement::Text("T-0260 edited paragraph marker"))`
  emitted 4 reflowed lines, the session accepted it, `save()` wrote the file, and
  a fresh session extracted the marker from page 1. `revisions=0` on the reopened
  session is expected (history starts at the saved bytes); the append is
  evidenced by the working session reaching 3 revisions and by the file growing
  from 119,341 to 196,824 bytes before signing.
- **Highlight.** `add_highlight` produced `/NM pdfxi-highlight-79` with
  `kind=Highlight`; after save/reopen `list_annotations` returns it with the
  scenario author and contents.
- **Comment thread.** A `/Text` note `pdfxi-t0260-note-1` plus a reply
  `pdfxi-reply-81` whose `parent` is that note. Three annotations are listed on
  page 1 (highlight, note, reply) after save/reopen.
- **Fill a form.** The self-produced AcroForm fixture exposes
  `["text-field", "checkbox-field", "choice-field"]`. Importing one XFDF value
  applied 1 field; after save/reopen the text field reads
  `Text("T-0260 form value")`.
- **Sign.** The signed file keeps the edited bytes as an exact prefix and adds
  one incremental revision (`byte_range=[0, 197466, 213852, 751]`, covering the
  whole 214,603-byte file). `verify_signature` reports `Valid`,
  `signature_valid=true`, `bytes_match=true`, `covers_entire_file=true`, signer
  `CN=PDFXI Test Signing Identity,O=PDFXI`, fixed signing time 1700000000.
- **Export to Word.** `ExportFormat::Docx` returned one part (7,921 bytes,
  `page_count=3`, `unsupported=[]`) that starts with `PK`, contains the `word/`
  directory and stores the edited paragraph marker verbatim (the OOXML writer
  uses deterministic stored ZIP entries, so a byte search is valid).
- **PDFium reopen.** The independent PDFium backend opens the saved signed file:
  3 pages, page 0 = 720.0 x 405.0 pt (the 16:9 PowerPoint slide size), no
  security handler.

## 8. Deviations and limits

1. **No Word-produced PDF (declared).** Word COM save/export is blocked
   (`orchestration/blockers/T-0215-word-com.md`). The multi-page route is the
   committed PowerPoint-produced `fixtures/realworld/powerpoint-slides.pdf`
   (3 pages, 119,341 bytes, producer `powerpoint`). No Word document is claimed.
2. **Signing identity is local and gitignored.** The scenario uses
   `crates/pdfxi-security/tests/fixtures/pfx/leaf-aes256.pfx`, which is generated
   by the committed `generate.ps1` and excluded by `.gitignore:25`
   (`crates/pdfxi-security/tests/fixtures/pfx/*.pfx`); private containers are
   never committed. The public password `pdfxi-test-pfx` is the documented test
   value. The existing `cargo test -p pdfxi-document --test signing -- --ignored`
   helper uses the same container and the same assertions.
3. **Assistant step skipped** for the reason in section 5.
4. **One procedural run.** The scenario checks are deterministic functional
   assertions (page counts, markers, annotation listings, signature status),
   not timings, so a single run is the evidence. Open/edit/save numbers are cited
   from T-0260B's five-round measurement instead of being re-measured.
5. **PDFium reopen scope.** The independent reader asserted page count and page-0
   geometry from PDFium's own document metadata and page object. PDFium text
   extraction was not used in this instrument because the release rlib graph
   contains two distinct `pdfxi_text` hashes (one pulled by
   `pdfxi-render --features pdfium`); the app's own PDFium text tests remain the
   text oracle.
6. **Docx text check is a byte search.** The OOXML writer stores XML parts
   uncompressed (`office_export/zip.rs`), so searching the archive bytes for the
   marker is valid for this writer. Office itself was not launched: A-27's "Office
   opens the result" is not claimed here, only structural validity (`PK`, `word/`
   part, title, page count).
7. **Fixture scope.** The corpus is 1-3 pages and 1-119 KiB; it does not stand in
   for 50 MB documents. That limit is already recorded in T-0260B.
