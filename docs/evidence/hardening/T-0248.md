## 2. Appearance algorithm

For each widget of a filled field:

1. Read the widget `/Rect` (normalized so left/bottom are minima) and
   `/MK /R`. `/R` is normalized modulo 360; only 90, 180 and 270 rotate, any
   other value (including non-multiples of 90) is treated as upright.
2. Choose the appearance-local box. Upright and 180°: `W × H`. 90° and 270°:
   `H × W`. The text therefore lays out along the long edge and is rotated into
   place by the matrix, instead of being squeezed into the short edge.
3. Build the field model (`Field`) and `WidgetAppearance` in that local box.
   `/Q` 0/1/2 maps to left/centre/right. The `/DA` size is used when positive;
   `0` uses the auto rule of §4.
4. Resolve the `/DA` font and encode the value (§3). Text and choice widgets use
   the resolved encoder; if no usable font exists the base-14 path is used and
   the reason is recorded.
5. `build_appearance_with_encoder` emits the stream in local coordinates with
   `/F1` as its placeholder `Tf` resource; the placeholder is replaced byte-wise
   with the resolved resource name.
6. Compute `/Matrix` as the rotation that maps the local box back into
   `[0, W] × [0, H]`: identity for 0°, `[0 1 -1 0 H 0]` for 90°,
   `[-1 0 0 -1 W H]` for 180° and `[0 -1 1 0 0 W]` for 270°. A non-identity
   matrix is written to the stream dictionary; an upright widget carries no
   `/Matrix` at all.
7. Write `/BBox [0 0 local_width local_height]`, `/FormType 1` and a
   `/Resources /Font` dictionary mapping the resource name to the resolved font
   object (a reference to the document's own font, never a re-embedding).
8. Buttons stay stateful: `/AP /N` remains a named state dictionary and `/AS`
   is selected from the value, so rotating a checkbox does not lose its active
   state.

`WidgetAppearanceReport` records the widget id, the font decision, the rotation,
the matrix and local BBox, and the union of laid-out text line boxes in
appearance space (`text_rect`). A caller can therefore prove placement without
re-parsing the content stream.

## 3. Font resolution and fallback rules

Lookup order for the `/DA` resource name (sanitized to `[A-Za-z0-9_-]`):

1. the widget page's `/Resources /Font` (the resolved page resources, including
   inherited resources);
2. `/AcroForm /DR /Font`;
3. otherwise `AppearanceFont::Fallback { reason: MissingResource }`.

Classification:

- `Type1`, `TrueType`, `MMType1` are simple fonts. With `/ToUnicode` the map is
  inverted (code to single character); without it the encoder uses WinAnsi plus
  printable ASCII, or printable ASCII alone for every other base encoding.
- `Type0` is supported only with `Identity-H` or `Identity-V`. Without
  `/ToUnicode` it is unsupported. A named CMap such as `UniJIS-UCS2-H` has a
  code space this build does not model, so it reports
  `Fallback { reason: UnsupportedFont }` rather than writing codes that might be
  wrong.
- `/ToUnicode` destinations of more than one UTF-16 unit (ligatures) are not
  encoded; the first code for each character wins, which keeps output
  deterministic.
- Embedded detection follows `/FontDescriptor` and checks `FontFile`,
  `FontFile2` and `FontFile3`; for `Type0` the descendant font's descriptor is
  used. `AppearanceFont::FieldFont { embedded }` reports the result.

Encoding:

- simple fonts: one-byte codes emitted as a literal string, escaped by
  `escape_literal_bytes`;
- composite fonts: two-byte CIDs emitted as a hexadecimal string;
- a value with any unencodable character falls back for the whole widget with
  `FallbackReason::CannotEncode` (never a partial or silent substitution).

Fallback path:

- a fresh base-14 Helvetica with `/WinAnsiEncoding` is staged under the
  sanitized `/DA` name; the appearance stream's own `/Resources /Font` shadows
  any page or `/DR` entry of that name for this stream only;
- the text is written with `WinAnsiEncoder` when the value fits WinAnsi (so `€`
  becomes byte `0x80` under the declared WinAnsi Helvetica), otherwise with the
  pre-existing UTF-16BE literal path;
- the fallback font object is always new, so a `/DA` font that resolved but
  could not encode the value is never referenced by the fallback appearance.

Documented limits: no glyph-coverage inspection inside an embedded program (an
embedded simple font is trusted for the bytes its encoding defines, which is the
viewer assumption for a well-formed font); no CID subsetting (the existing font
object is referenced, the program is never rewritten); `MacRomanEncoding`,
`StandardEncoding`, `PDFDocEncoding` and custom `/Differences` are honoured for
printable ASCII only; page `/Rotate` is ignored (widgets are placed in unrotated
page space, which is what annotation coordinates mean).

## 4. Auto font size

`/DA` size `0` now uses `(local_height - 4).clamp(4, 12)` points, the
documented 0..12 auto heuristic. This *changes generated sizes* versus T-0234,
which used `((height - 4) * 0.8).clamp(4, 24)`: a 20-point field is now 12
points instead of 12.8, and tall fields are capped at 12 instead of 24. No test
depended on the old numbers; the change is recorded because appearance bytes
differ for size-0 fields.

## 5. Matrix math and flattening

`Matrix::fit_bbox(appearance, bbox, left, bottom, width, height)` implements the
ISO 32000-1 §12.5.5 placement rule:

1. transform the four `/BBox` corners by the appearance `/Matrix` and take the
   axis-aligned bounds `(x0, y0, x1, y1)`;
2. reject a degenerate transformed box (either extent ≤ 1e-9) or non-finite
   input;
3. return `appearance · translate(-x0, -y0) · scale(W/(x1-x0), H/(y1-y0)) ·
   translate(left, bottom)`.

Flatten uses exactly this matrix as the `cm` operator before `/FmN Do`. The
previous flatten code assumed an identity appearance matrix and only scaled
`/BBox` into `/Rect`; it now composes rotation as well. For the test widget
(`/Rect [300 450 500 490]`, `/MK /R 90`, local BBox `40 × 200`, matrix
`[0 1 -1 0 200 0]`) the emitted operator is `0 1 -1 0 500 450 cm`, which maps
local `(0,0)` to `(500,450)` and `(0,200)` to `(300,450)` — the two ends of the
widget's vertical text band.

Remaining matrix limits: page `/Rotate` is not composed (see §3); a widget whose
`/Rect` is degenerate gets no appearance; a non-finite or singular `/Matrix` on
a pre-existing appearance is treated as identity for flattening rather than
failing the whole flatten.

embedded fonts and the rotated fields are staged into a *copy* of the committed

`crates/pdfxi-edit/assets/CourierPrime-Regular.ttf` when present, with a
synthetic sfnt header as the fallback, so the test is portable and needs no new
asset. Every artifact above is therefore self-produced and labelled as such.

## 10. Limits and remaining work

1. Named non-identity composite encodings, multi-character `/ToUnicode`
   destinations and non-ASCII characters outside WinAnsi take the fallback.
2. No glyph-coverage parsing of the embedded program and no CID subsetting; the
   existing font object is referenced unchanged.
3. `MacRomanEncoding`, `StandardEncoding`, `PDFDocEncoding` and `/Differences`
   are ASCII-only.
4. Page `/Rotate` is not composed into widget coordinates.
5. PDFium does not link into this lane; the orchestrator should reopen
   `filled-font.pdf` (embedded glyphs visible) and `rotated.pdf` (vertical text
   inside the 200 × 40 rect) for the independent render check.
6. The app shell task T-0243 still has to expose fill with these appearances and
   promote FORMS-001/FORMS-006/FORMS-007 from `library` to `verified`.
7. XFA import/render and the bounded JavaScript/calculation interpreter remain
   out of this library round.
