## 1. Why

A-23 is only half-done when the user can add content but cannot touch content
that is already on the page. The library needs to enumerate what is selectable,
move it, resize it, replace it and delete it, and every operation must go
through the caller's `pdfxi-document` session snapshot so ADR 0010 undo/redo
works. Proof must be a second reader rendering the page: re-extraction alone
would pass even if the object still painted at the old place.

Round A (move and delete) and Round B (resize and replace) are both in
`pdfxi_edit::content_edit` on the real fixture
`fixtures/realworld/microsoft-excel-2019-sample.pdf` (hybrid xref, object
stream, Flate content, subset Calibri). All edits are copy-on-write through
`pdfxi_core::Document::set_object`; source bytes are never mutated.

## 2. Public API (`pdfxi_edit::content_edit`, re-exported at the crate root)

```rust
pub fn list_objects(document: &Document, page_index: usize)
    -> Result<Vec<PageObject>, ObjectEditError>;

pub fn move_object(document: &mut Document, page_index: usize, id: &str,
                   dx: f64, dy: f64) -> Result<(), ObjectEditError>;

pub fn resize_object(document: &mut Document, page_index: usize, id: &str,
                     sx: f64, sy: f64) -> Result<(), ObjectEditError>;

pub fn replace_object(document: &mut Document, page_index: usize, id: &str,
                      replacement: ObjectReplacement<'_>)
    -> Result<ObjectReplaceOutcome, ObjectEditError>;

pub fn delete_object(document: &mut Document, page_index: usize, id: &str)
    -> Result<(), ObjectEditError>;
```

Supporting types:

- `PageObject { page: usize, id: String, kind: ObjectKind, rect: Rect,
  text_preview: String }`.
- `ObjectKind::{TextBlock, Image}`.
- `ObjectReplacement<'a>::Text(&'a str)` and
  `ObjectReplacement<'a>::Image { bytes: &'a [u8], format: ImageFormat }`.
- `ObjectReplaceOutcome { page_index, id, kind, text_lines: Option<usize>,
  pixel_width: Option<u32>, pixel_height: Option<u32> }`.
- `ObjectEditError` with typed variants for the core reader/writer, the text
  model, missing and invalid identifiers, non-finite or oversized move deltas,
  moves and resizes that leave the page, invalid scales, shared text objects,
  shared image resources, replacement-kind mismatch, unsupported content,
  malformed content, invalid byte spans, oversized content, and reference-graph
  limits.

`T-0233`'s API is unchanged: `text_blocks`, `replace_run_text`, `add_text_box`,
`add_image`, `PageTextModel`, `TextBlock`, `TextLine`, `TextRun`, `TextAlign`,
`ImageFormat`, `FontChoice`, `ReplaceOutcome`, `TextPlacement`,
`ImagePlacement`, `TextEditError`.

## 3. Identifier stability

Identifiers are derived from the current page state, never from PDF object
numbers:

- `text:<block-index>` - the zero-based block index in
  `PageTextModel::blocks` reading order.
- `image:<resource-name>:<occurrence>` - the page resource name without its
  leading slash plus the zero-based occurrence of a `Do` operator that names
  that resource, in content-stream order.

An identifier stays valid while the page content and its text/image model are
unchanged. Every move, resize, replace or delete rewrites page content, so
callers must call `list_objects` again after an edit. A move and a resize keep
the number and order of show operators and `Do` operators, so their own
identifier remains valid for a following operation in the same revision; a
replace reflows the block and a delete removes operators, so re-listing is
mandatory after those.

## 4. Move rewrite strategy

### 4.1 Text blocks

`move_object` scans text objects (`BT`...`ET`) and attributes each visible show
operator to a block from the text model. A block is moved by rewriting only its
placement operators:

- every `Tm` that positions the block is translated, with the user-space delta
  mapped back through the content matrix in effect (`text_space_delta`);
- when a block is positioned only by `Td`/`TD` or by the default text matrix,
  one translated relative move is written (or a `1 0 0 1 dx dy Td` is inserted
  at the first show) so the block shifts without touching its text.
Text, fonts, colours, clips, marked content (`BDC`/`EMC`) and every other block
stay byte-identical.

### 4.2 Images

The translation is added to the `cm` that places the image immediately before
its `Do`, inside that draw's existing `q`/`Q` pair. Only the selected
occurrence moves; other images, including other usages of the same XObject,
keep their placement. A draw inside a text object, without its own `q`/`Q`
pair, sharing its placement matrix with another draw, or under a scaled or
rotated parent transform is rejected as unsupported rather than moved by an
approximate amount.

A move that would leave the page entirely is rejected with
`MoveOutOfBounds`. Both delta components must be finite and at most 1,000,000
user-space units in absolute value.

## 5. Delete and orphan cleanup

### 5.1 Text blocks

Every text object fully owned by the block is removed, including its `BT` and
`ET`, so no show or positioning operator from the block survives. Surrounding
marked content, graphics state, clips and other blocks are preserved. Font
resources are *not* removed: a font may be shared with content that is still
present. A text object that also contains visible text outside the block is
rejected with `SharedTextObject`.

### 5.2 Images

The `Do` usage is removed. When this was the only usage in the document, the
page resources and `/XObject` dictionary are not shared with another page, and
the object is only referenced from this page's XObject dictionary, the resource
entry is removed and the XObject is replaced with `null`, leaving no orphan. A
shared image keeps its object and resource entry; only this page's usage is
removed.

## 6. Shared-object fail-closed rules

The library refuses an approximate rewrite instead of guessing:

- text object owned by the block plus another block, or containing a visible
  show the model did not record: `SharedTextObject`;
- image draw inside a text object: `UnsupportedContent`;
- image draw without its own placement `cm`: `UnsupportedContent`;
- two draws sharing the same placement matrix: `UnsupportedContent`;
- image draw outside a `q`/`Q` pair: `UnsupportedContent`;
- image draw under a scaled or rotated parent transform:
  `UnsupportedContent`;
- resize of rotated or non-axis-aligned text: `UnsupportedContent`;
- resize of text positioned without a `Tm` or without a `Tf`:
  `UnsupportedContent`;
- replace of an image stored directly in the resource dictionary rather than
  as an indirect object: `UnsupportedContent`;
- replace of an image XObject with more than one usage, more than one
  reference, or a shared page resource / XObject dictionary:
  `SharedImageResource`.

## 7. Effective-document reparse cost

`pdfxi-core` has no accessor for staged, not-yet-saved objects (the same
limitation T-0230 and T-0233 document). Every public operation therefore calls
`effective_document`, which is

```rust
let bytes = document.save_incremental()?;
Document::from_bytes(bytes)
```

That is one incremental append plus one full parse of the document per
operation (and `list_objects` does one parse). It is O(document) work and
allocates the parsed object graph; it is acceptable for one interactive
object edit at a time but is not free. Tests that chain several operations are
therefore O(document x operations). A future core staged-object reader would
remove the reparse without changing this API. No unbounded work is added: the
reference walk for delete/replace is capped at depth 64 and 200,000 objects and
returns typed limit errors.

## 8. Resize (Round B)

### 8.1 Images

`resize_object` rewrites the image's placement `cm` in place. For
`[a b c d e f]` the two axis vectors are scaled and the translation is kept:

```text
[a*sx  b*sx  c*sy  d*sy  e  f] cm
```

For the normal axis-aligned placement (`a = width`, `d = height`, `b = c = 0`)
this scales the box about its lower-left origin. Rotation or shear already in
the matrix stays on the same axis vectors; a uniform scale preserves the angle,
while an anisotropic scale changes it exactly as scaling the box would. The new
page rectangle is the image unit square transformed by the new matrix and the
parent CTM. The operation fails closed exactly like a move for a shared
placement matrix, a draw inside text, a missing placement, no `q`/`Q`, or a
non-identity parent transform. `sx` and `sy` must be finite, positive and at
most 1000; a resize that leaves the page entirely is `ResizeOutOfBounds`.

### 8.2 Text blocks

Text is scaled about the block rectangle's origin `(x0, y0)` without changing
the font resource, so it stays extractable and other blocks stay untouched:

- every `Tf` inside the block's text objects is rewritten to
  `size * sy`, which scales glyph height and the model's height estimate;
- every `Tm` linear term `a` becomes `a * (sx / sy)` (the horizontal
  correction, because the larger font size already scales advance by `sy`);
  `d` is left alone so height is not scaled twice;
- `Tm` translations are mapped about the block origin through the content
  matrix, and `Td`/`TD` operands are multiplied by `sy`, so multi-line spacing
  and relative moves scale with the new font size.

Net effect: glyphs, advances, line pitch and the model rectangle scale by
`(sx, sy)`. The operation requires axis-aligned `Tm` matrices (`b = c = 0`), a
linear-identity content transform, at least one `Tm` and at least one `Tf`
inside the object, and a text object owned only by the block; otherwise it
fails closed with `UnsupportedContent` / `SharedTextObject`. Non-positive,
non-finite or oversized scales are `InvalidScale`; a result that leaves the
page is `ResizeOutOfBounds`.

Limits: a single text object that mixes several font sizes is scaled per `Tf`
(so each part scales uniformly by `sy`); character/word spacing (`Tc`/`Tw`)
is not multiplied by the scale; rotated text and text positioned only by
relative moves are refused rather than stretched approximately.

## 9. Replace (Round B)

### 9.1 Text blocks

`replace_object(..., ObjectReplacement::Text(text))` rebuilds the whole block
through the T-0233 path. The block's paragraph text is the replacement, with
line breaks treated as paragraph separators joined by a single space. The
existing `replace_run_text` internals were factored into `rebuild_block`,
which:

1. reuses the first run's font only when it is a simple, non-subset font that
   can encode the whole paragraph, otherwise embeds the bundled Courier Prime
   SIL OFL fallback as a Type0/CID font with `/W`, `/ToUnicode` and
   `/CIDToGIDMap`;
2. reflows greedily at the block's existing width with one font per block;
3. splices every show operator of the block with the re-emitted lines at the
   first run's baseline, preserving clips, colours, marked content and all
   other blocks.

`replace_run_text` keeps its exact previous behaviour and now shares this
helper. The outcome reports the reflowed line count and font choice.

### 9.2 Images

`replace_object(..., ObjectReplacement::Image { bytes, format })` decodes the
new PNG (8-bit grey/RGB/RGBA/grey+alpha/palette, all five scanline filters via
the core Flate path) or reads the JPEG markers and keeps the original bytes as
`/DCTDecode`. The image XObject stream and dictionary are replaced in place
with the same `image_stream_dictionary` helper `add_image` now uses:

- the resource name and the `Do` placement are unchanged, so position, size,
  rotation and page content stay byte-identical;
- `Width`, `Height`, `ColorSpace`, `BitsPerComponent`, `/Filter` and the pixel
  bytes come from the new image;
- a draw whose XObject is used more than once, referenced from more than one
  place, or whose page resource / XObject dictionary is shared with another
  page is rejected with `SharedImageResource`, because replacing it would
  change content the caller did not name.

An image stored directly in the resource dictionary has no stable object to
replace and is refused. Decoder failures surface as the typed
`TextEditError::Png` / `Jpeg` variants through `ObjectEditError::Text`.

## 10. PDFium render proof

`crates/pdfxi-edit/tests/object_render.rs` loads PDFium at runtime, rasterizes
the saved bytes at scale 1.0 before and after each edit, and measures page
coordinates. It is the independent reader: text extraction alone cannot prove
where an object paints.

Round A:

- `moved_text_extracts_and_renders_at_its_new_position` - added text box,
  moved by `(30, -40)`. The old crop must lose its ink (assertion `<= 2`
  pixels) and the destination crop must gain more than 20 dark pixels. PDFium
  character boxes must move by the same delta within 2-3 pt.
- `moved_image_renders_at_its_new_position` - solid red 8x8 PNG placed at
  `(72,300)-(172,400)`, moved by `(150,-50)`. Old crop must have zero red
  pixels; destination crop must have more than 500.
- `deleted_text_and_image_leave_no_content` - deleted text and image crops must
  contain zero dark / zero red pixels while unrelated text still has ink and
  extraction still contains the kept text.

Round B adds two tests with these measured numbers (scale 1.0, page 612 x 792):

- `resized_text_and_image_render_at_scaled_bounds` - 1.5 x 1.5 text resize.
  PDFium dark-ink extent went from `(73,556)-(265,580)` (192 x 24 pt) to
  `(73,556)-(362,592)` (289 x 36 pt): width ratio 1.505, height ratio 1.500,
  left and bottom edges unchanged, so the ink really scaled about the block
  origin. The image was resized 1.5 x 0.5: the band above its new top went from
  500+ red pixels to **0**, and the strip beyond its old right edge went from
  **0** to **2250** red pixels.
- `replaced_text_and_image_extract_and_render` - after replacing the text and
  the red image with blue, the text crop had **491** dark pixels, the image
  crop had **10000** blue pixels and **0** red pixels, and PDFium extraction
  contained `After replacement words` and not `Before replacement words`.

Round A numbers from the same run: the moved text satisfied the old-crop
`<= 2` ink bound and gained more than 20 dark pixels at the destination; the
moved image lost its old crop (asserted 0 red) and gained more than 500 red
pixels; deleted text/image crops rendered 0 dark / 0 red pixels while unrelated
text stayed inked.

Thresholds are calibrated against the unedited fixture in the same run; a
missing native PDFium library fails these tests with a clear backend error.

## 13. Limits

- Round A does not enumerate images inside `/Form` XObjects and does not
  handle inline images (`BI ... ID ... EI`); both are skipped/refused.
- Move/resize/replace are single-object operations; there is no multi-select
  transform and no marquee selection.
- `list_objects` reports text blocks from the existing text model and image
  XObjects drawn directly by the page content stream; vector paths, shadings,
  annotations and form widgets are not selectable objects in this API.
- Text resize is horizontal/vertical scaling of existing glyphs, not a font
  re-selection; a mixed-size block scales each `Tf` uniformly, `Tc`/`Tw` are
  not multiplied by the scale, and rotated or relative-placement-only text is
  refused.
- Text replacement uses the T-0233 reflow model: one font per block, greedy
  wrap, no justification, no hyphenation, horizontal text only.
- Image replacement keeps the resource name and the single placement; it
  refuses an image used more than once or shared with another page, because
  swapping the XObject would change draws the caller did not name. JPEG
  replacement keeps the original encoded bytes (no re-encode). Alpha channels
  are still ignored in Rounds A and B.
- Resize of an image stored inside a Form XObject, of an inline image, or of a
  text block under a scaled/rotated content transform is not attempted; those
  objects are not listed or fail closed.
- Every operation pays one full reparse (`effective_document`, section 7).
- The shell task for the selection overlay and handles is separate; this
  library task reports `library` status, not GUI-reachable `verified`.
