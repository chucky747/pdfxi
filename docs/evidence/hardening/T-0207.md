# T-0207 - incremental save for cross-reference-stream sources

Date: 2026-11-20
Toolchain: rustc 1.100.0 (0ef1bc386 2026-11-09), cargo 1.100.0 (3acc79c0c 2026-11-05)
Target dir: `CARGO_TARGET_DIR=target/lanes/core`
Task: T-0207, lane `core`, claim `orchestration/claims/T-0207.json`

## 1. What was wrong

`Document::save_incremental()` declined every source whose parsed cross-reference
layer contained a stream. That covers all hybrid files (Excel's output) and every
pure xref-stream producer, so the write path could not append to modern PDFs even
though the parser and the incremental writer already understood both section
kinds.

## 2. What changed

`crates/pdfxi-core/src/lib.rs`

- `Document::save_incremental()` no longer duplicates the classic writer. It
  keeps the stored structural error for unreadable input, keeps
  `Error::UnsupportedState("encrypted documents cannot be saved")` for `/Encrypt`
  sources, then selects the appended section kind from the byte at the final
  `startxref` (`parser::looks_like_xref_stream`) and delegates to
  `Document::save_incremental_with()`.
  - Final section is a cross-reference stream -> new `/Type /XRef` stream with
    `/W [1 4 0]`, `/Index`, `/Size`, `/Prev`, `/Root`/`/Info`/`/ID` carried over.
  - Final section is a classic table -> classic table (this includes the Excel
    hybrid fixture: its `startxref` points at the classic table that carries
    `/XRefStm`, so the update stays classic).
- Full-rewrite `Document::save()`, `optimize()` and `apply_page_plan()` are
  unchanged and still decline xref-stream sources with
  `Error::UnsupportedState`.

`crates/pdfxi-core/src/incremental.rs`

- Removed the `structure.xref.uses_xref_stream` rejection from
  `save_incremental_with()`; the stream branch already existed and is now
  reachable. `IncrementalSaveOptions.xref_kind` still wins for an explicit
  caller, and the documentation says so.
- Added `strip_xref_stream_keys()` before either section is emitted. A merged
  trailer from a hybrid or stream source carries `/Type /XRef`, `/W`, `/Index`,
  `/Length`, `/Filter`, `/DecodeParms` and `/DL` from the companion stream. Left
  in place those keys would make a new classic table claim a stream body, and a
  new unfiltered stream claim the old `/Filter`; skipping the strip made the
  pure-stream round trip fail to reparse.
- `/XRefStm` is still removed from the new classic trailer, and the second `/ID`
  element is still regenerated deterministically.
- Updated rustdoc for `save_incremental_with()`, `plan_incremental_update()` and
  `IncrementalSaveOptions`.

`crates/pdfxi-core/src/xref_tests.rs`

- `xref_stream_parses_page_tree_content_and_decode_parms` now asserts that the
  full rewrite still declines, but the incremental save succeeds and preserves
  the source prefix.
- New `incremental_save_of_xref_stream_source_appends_matching_stream_section`:
  a pure, non-hybrid xref-stream PDF (FlateDecode, built byte by byte in the
  test) stages a replacement content stream through `Document::set_object`,
  calls `save_incremental()`, and asserts:
  - the saved bytes start with the original bytes;
  - the new section is a stream whose `/Prev` equals the source `startxref`;
  - the reparsed document's page text is the updated text.

`crates/pdfxi-core/tests/realworld.rs`

- `real_world_pdf_text_and_current_save_limitation` renamed to
  `real_world_pdf_text_is_extractable`; the old limitation assertion is gone,
  all page/text assertions are unchanged.
- `real_world_pdf_incremental_save_preserves_pages_and_text` lost `#[ignore]`
  and its assertions were extended, not weakened: the Excel 2019 hybrid source
  round-trips bit-prefix-exact, both pages keep their text, the appended section
  is a classic table, and the appended bytes contain no `/XRefStm`.

Every new assertion failed before the change: `save_incremental()` returned
`Err(Error::UnsupportedState("cross-reference streams are not supported"))` at
the removed guard, so each test stopped at its `.expect(...)` / limitation match.

## 4. Scope and limitations

- New revisions write only type-1 (plain indirect) entries; compressed source
  objects keep their type-2 entries in the older section and are never rewritten
  as object streams. No new object streams are produced.
- Encryption is still rejected: incremental saves do not encrypt, so an
  `/Encrypt` source returns `Error::UnsupportedState`. Encrypted xref-stream
  sources therefore remain unsupported.
- Full rewrite (`save()`), the optimizer and page-plan output still decline
  xref-stream sources; this task only unblocks incremental appends.
- The xref stream writer uses `/W [1 4 0]`; a source object offset above 4 GiB
  is rejected with `Error::CannotSerialize` rather than truncated.
- The entry rows are written uncompressed. No `/Filter` is emitted, so a source's
  filter keys must not leak (covered by `strip_xref_stream_keys`).
- No independent reader (pdfium/qpdf) was available in this lane to cross-check
  the appended bytes; verification is by reparse through `pdfxi-core` plus the
  `/Prev` and prefix assertions.
- No tracked benchmark covers incremental save. The change does not add a pass
  over the source: the same single `Vec` clone is made by the shared
  implementation, and the appended bytes are unchanged in size for classic
  sources.
- Integration note: the old test name `real_world_pdf_text_and_current_save_limitation`
  is still listed in `orchestration/feature-updates/T-0204.toml` and
  `docs/evidence/hardening/T-0204.md`. Those are historical/integrator-owned;
  the citation index will not resolve the old name until the integrator updates
  the T-0204 fragment.
