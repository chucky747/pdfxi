## 1. What shipped

- `fixtures/realworld/` - five committed PDFs produced by mainstream software
  where one exists, plus two clearly labelled self-produced files for the slots
  no installed producer on the reference host can fill.
- `fixtures/realworld/manifest.toml` - the machine-readable source of truth:
  producer, SHA-256, leaf page count, marker words, and any recorded current
  limitation, one `[[fixture]]` table per file.
- `crates/pdfxi-testkit/tests/realworld_corpus.rs` - five deterministic,
  offline tests over that directory (checksums, manifest/directory agreement,
  field sanity, core open + page count, text markers or recorded limitation).
- `crates/pdfxi-testkit/examples/generate_realworld_selfmade.rs` - regenerates
  the two self-produced files from committed fixtures.
- `fixtures/realworld/generate.ps1` - the Office/Edge automation and copy step.
- `fixtures/realworld/README.md` and `docs/CORPUS.md` - provenance, sizes,
  regeneration commands and the known gaps.
- `cargo xtask corpus smoke` now runs this suite too (integrator commit
  `ac9db95`, `xtask/src/main.rs::corpus_smoke`), so the corpus is part of the
  corpus gate rather than a test someone has to remember.

The suite deliberately has no `#[ignore]`d assertions and no network access; it
reads only files committed in this repository.

## 3. Manifest and gate

Manifest: `fixtures/realworld/manifest.toml` (fields documented in its header).
`known_failure` is the honesty mechanism: the test asserts the marker words are
still **absent** and that some text is still returned, so fixing the parser
turns the suite red until the manifest entry is updated. `expected_error`
asserts a typed variant; only `UnexpectedToken` is modelled this round, and the
test rejects any other variant name in the manifest.

`cargo test -p pdfxi-testkit --test realworld_corpus`:


directions, so adding a PDF without a manifest row (or a stale row) fails.

## 4. Findings

1. **Edge subset font has no applied `ToUnicode` CMap.** `Document::page_text`
   succeeds for `browser-print.pdf` but returns glyph codes, not Unicode. This
   is a real text-extraction defect, not a fixture problem: the file is a
   normal headless-Edge print. T-0216 (lane `core`, P1) owns the fix and the
   manifest flips with it.
2. **Encrypted documents have no decrypt layer.** `page_text` returns
   `Error::UnexpectedToken` because the encrypted content stream is parsed as
   plaintext; the CLI surfaces it as
   `Error: unexpected token while parsing: unknown token: ...`. This is a
   limitation of `pdfxi-core`, not of the fixture: the file is genuinely
   AES-128 encrypted (revision 4) and opens/parses its page tree. T-0214 owns
   the decryption and typed password-error layer; T-0216 must not model it.
3. **Word automation cannot produce a fixture on the reference host.** Every
   `SaveAs2`/`ExportAsFixedFormat` call hangs indefinitely while
   `Documents.Add` works, so `word-multipage.pdf` and
   `word-tagged-bookmarks.pdf` are recorded as gaps in
   `orchestration/blockers/T-0215-word-com.md` (with the exact probe, the
   attempted fixes, host restoration, and the two viable next steps). PowerPoint
   COM export on the same host succeeds, which isolates the problem to Word.
4. **No installed producer for AcroForm or password-protected PDFs.**
   LibreOffice is absent and Word cannot export, so those two slots are
   self-produced and labelled as such rather than passed off as external
   samples.

## 5. Provenance and legal

- All page content is original text written for this repository. No third-party
  document, help text, icon or asset was copied or downloaded; the fixtures are
  not Adobe material.
- `generate.ps1` reads no network content. It writes intermediates under
  `target/tmp/realworld`, drives locally installed Office/Edge COM automation,
  invokes the testkit example, and copies the results into
  `fixtures/realworld/`.
- The self-produced AcroForm file is the committed
  `fixtures/authoring/authoring-forms.pdf` copied under its corpus name; the
  self-produced encrypted file is written by `pdfxi-security`'s encryption
  writer with a fixed document-ID seed so regeneration is byte-stable. Their
  passwords (`pdfxi-test` open, `pdfxi-owner` owner) are public test values, not
  secrets.
- Committed sizes stay small (266 KiB total) so clones and CI stay cheap.

## 6. Gaps and limitations

- `word-multipage.pdf` and `word-tagged-bookmarks.pdf` are missing; the blocker
  records why and what to try next (interactive Word first run or Office repair).
- No externally produced AcroForm or encrypted sample exists; both rows are
  self-produced and must stay labelled that way.
- Regeneration requires Office 2019/16.0 and Edge on the host. The committed
  bytes and hashes are the contract, so a machine without those producers can
  still run the suite; it just cannot regenerate.
- The manifest parser is a small hand-written reader (no `serde` in the test)
  that supports exactly the fields listed in the header. Adding a nested value
  would need a parser change.
- `browser-print.pdf` is 51 KiB and `powerpoint-slides.pdf` 119 KiB; both are
  small enough that a 10x larger corpus would still fit the fixture budget, so
  there is no size pressure yet.
