## 1. What shipped

- `crates/pdfxi-security/src/protect.rs` - the document-facing protect layer:
  `protect_document`, `remove_protection`, `ProtectOptions`,
  `ProtectPermissions`, and `MAX_PASSWORD_BYTES`.
- `crates/pdfxi-security/src/error.rs` - three typed variants:
  `DocumentAlreadyEncrypted`, `DocumentNotEncrypted`,
  `DocumentRewriteFailed(String)`, each with a `Display` arm. No existing
  variant changed meaning.
- `crates/pdfxi-security/src/lib.rs` - module registration, crate docs, and
  re-exports.
- `crates/pdfxi-security/tests/protect_document.rs` - four integration tests on
  `fixtures/realworld/microsoft-excel-2019-sample.pdf` plus unit tests in the
  module.

No new dependency, no new cipher, no hand-rolled crypto. The module calls the
existing `encrypt_document` and `open_encrypted` from
`encryption_writer.rs`, which in turn use `standard_handler` and `crypto`.
`pdfxi-core` full `Document::save` is the only rewrite path.

## 2. Public API

```rust
pub const MAX_PASSWORD_BYTES: usize = 127;

pub struct ProtectPermissions {
    pub print: bool,
    pub modify: bool,
    pub copy: bool,
    pub annotate: bool,
    pub fill_forms: bool,
    pub accessibility: bool,
    pub assemble: bool,

impl ProtectPermissions {

    pub fn to_permission(self) -> Result<Permission>; // validates dependencies
}
impl Default for ProtectPermissions { /* ALL */ }

pub struct ProtectOptions {
    pub user_password: Vec<u8>,
    pub owner_password: Option<Vec<u8>>,

    pub encryption: EncryptionMethod,
    pub revision: Option<u8>,
    pub encrypt_metadata: bool,
    pub id_seed: Option<Vec<u8>>,
}
impl ProtectOptions {
    pub fn new(user_password: impl AsRef<[u8]>) -> Self;
    pub fn with_owner_password(self, password: impl AsRef<[u8]>) -> Self;
    pub fn with_permissions(self, permissions: ProtectPermissions) -> Self;
    pub fn with_encryption(self, method: EncryptionMethod) -> Self;
    pub fn with_revision(self, revision: u8) -> Self;
    pub fn with_encrypt_metadata(self, value: bool) -> Self;
    pub fn with_id_seed(self, seed: Vec<u8>) -> Self;
    pub fn effective_owner_password(&self) -> &[u8];
    pub fn permission_mask(&self) -> Result<Permission>;
}
// Debug redacts both passwords and the seed length only.

pub fn protect_document(
    source: &pdfxi_core::Document,
    options: ProtectOptions,
) -> Result<Vec<u8>>;

pub fn remove_protection(bytes: &[u8], password: &[u8]) -> Result<Vec<u8>>;
```

Defaults: AES-256, revision 6, all permissions granted, `EncryptMetadata=true`,
owner password equal to the user password when `owner_password` is `None`.

Behavior:

- `protect_document` first runs a `pdfxi_core::Document::save` full rewrite. That
  expands `/ObjStm` members, flattens incremental revisions, and produces the
  classic `N G obj` layout the encrypting writer serializes. The writer then
  encrypts every live string and stream and appends the `/Encrypt` dictionary,
  `/Perms`, `/ID`, and trailer entry.
- `remove_protection` authenticates the bytes with the supplied password
  (user or owner), then runs `Document::save` on the decrypted document. The
  result has no `/Encrypt` entry and is a full rewrite, matching ADR 0010's
  "removing encryption cannot be an append" rule.
- An already-encrypted `Document` is rejected with `DocumentAlreadyEncrypted`
  (detected from the core save path, not by a content heuristic), so ciphertext
  is never encrypted twice.
- A plaintext input to `remove_protection` is rejected with
  `DocumentNotEncrypted`.
- Empty user and owner passwords together are rejected, and passwords over
  127 bytes are rejected rather than silently truncated.
- Contradictory grants (annotate or assemble without modify; high-quality print
  without print) are rejected with `PermissionConflict` before writing, so this
  crate never produces a file its own reader would reject.

## 3. Permission mapping

| Option field | `/P` bit | Mask | `Permission` |
|---|---|---|---|
| `print` | 3 | `1 << 2` | `PRINT` |
| `modify` | 4 | `1 << 3` | `MODIFY` |
| `copy` | 5 | `1 << 4` | `COPY` |
| `annotate` | 6 | `1 << 5` | `ANNOTATE` |
| `fill_forms` | 9 | `1 << 8` | `FILL_FORMS` |
| `accessibility` | 10 | `1 << 9` | `ACCESSIBILITY` |
| `assemble` | 11 | `1 << 10` | `ASSEMBLE` |
| `print_high_quality` | 12 | `1 << 11` | `PRINT_HIGH_QUALITY` |

The writer sets the reserved always-1 bits and clears bits 1-2
(`Permission::to_p_word`). The test file's restricted grant (print, fill,
accessibility, high-quality print, no copy, modify, annotate, assemble) writes
`/P -1084`, i.e. `0xFFFFFBC4`, and reopens to exactly that mask.

| RC4-40 | 1 | 2 | RC4 40-bit | `explicit_aes128_and_rc4_revisions_are_covered` |

AES-256 revision 6 is the default and the only method used by the acceptance
path. RC4 and AES-128 are available for compatibility.

## 5. Session integration (documented, not modified)

`pdfxi-document` is outside this claim and was only checked for compatibility.
Its `DocumentSession::bytes()` returns decrypted plaintext for an encrypted
source. The app flow documented in `protect.rs` is:

1. Edit through the session as usual.
2. Call `protect_document` on the session document (or a `Document` parsed from
   `session.bytes()`) with the user's passwords and grants.
3. Write the returned bytes atomically, or load them with
   `DocumentSession::open_bytes_with_password`; the result is a new session.
4. Do not let the old session save over the protected file: the session still
   returns `EncryptedSaveUnsupported` by design.

Protection and removal are full rewrites, so they flatten revisions and
invalidate signatures that covered earlier bytes; the shell must tell the user,
as ADR 0010 point 5 requires.

## 9. Limits and follow-ups (honest)

- **Permissions are advisory.** The `/P` mask and AES-256 `/Perms` are
  authenticated, but a reader that ignores them opens the document anyway, and
  the owner password always bypasses the mask. `pdfxi-core` text extraction does
  not consult `Permissions`; the shell must enforce the UI policy and explain it.
- **AES-256 file-key randomness.** The existing writer derives the file key
  deterministically from the document `/ID` and both passwords
  (`derive_file_key` in `encryption_writer.rs`). This is not a fresh random key
  and is a pre-existing writer property; replacing it needs a vetted RNG and a
  revision-6 update in the writer. `id_seed` only affects sources without `/ID`.
- **Trailer metadata.** The shared writer emits a minimal trailer (`Size`,
  `Root`, `ID`, `Encrypt`), so `/Info` is not referenced in protected output; the
  same is true of the decrypted rewrite. Page content, page count, and page text
  are preserved. Preserving `/Info` is a writer-level follow-up, not a change
  to cryptography.
- **No PFX / certificate encryption.** This task covers standard password
  protection only. Certificate encryption remains T-0249.
- **No independent PDFium reopen in this round.** The tests use this crate's
  `open_encrypted` as instructed. The acceptance note's PDFium reopen (with the
  password, fail without it) belongs to the serialized shell task / round B;
  no PDFium or external PDF CLI is available in this lane's gate.
- **No shell wiring.** Per ADR 0012 this row stays `library`; the app shell task
  owns the dialog, the explanation of advisory permissions, and the final
  `verified` status.
- Signed and linearized inputs are refused by the existing writer rather than
  silently rewritten, because protecting them would invalidate or discard
  structure without the user's knowledge.
## Known limitations (orchestrator review)

Recorded after the orchestrator's review of this round. These are
cryptographic-quality defects to fix before release; they are not a claim that
the current output is exploitable. Follow-up: **T-0256** (use a CSPRNG file key
for AES-256 and preserve `/Info`), `orchestration/tasks/T-0256.json`.

- **Deterministic AES-256 file key.** The writer derives the file key
  deterministically from the document `/ID` plus both passwords
  (`derive_file_key` in `encryption_writer.rs`) rather than drawing a random
  32-byte file key and wrapping it through `/UE` and `/OE` per ISO 32000-2
  revision 6. Two protects of the same source with the same passwords therefore
  share key material. T-0256 replaces this with a CSPRNG and R6 salts and adds
  a test that the outputs differ.
- **Lost `/Info`.** protect and remove-protection emit a minimal trailer
  (`Size`, `Root`, `ID`, `Encrypt`), so the `/Info` reference disappears from
  protected and decrypted output. Document metadata is not preserved. T-0256
  carries the trailer key through.
- **No independent reader in this round.** The tests reopen the output with the
  same crate that wrote it (`open_encrypted`), so round-trip agreement does not
  prove interoperability. T-0256 adds a PDFium reopen (and a second reader
  where available).

The test results above are unchanged by this note.
