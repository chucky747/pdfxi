# T-0256 - CSPRNG AES-256 file key and `/Info` preservation

Date: 2026-11-20
Task: T-0256, lane `security`, claim `orchestration/claims/T-0256.json`
Follow-up to: T-0238 (`docs/evidence/hardening/T-0238.md`, Known limitations)
Acceptance: two protects of the same source with the same passwords produce
different file keys, and an independent reader opens the result while `/Info`
survives.
Target dir: `CARGO_TARGET_DIR=target/lanes/security3`
Toolchain: rustc 1.100.0 (0ef1bc386 2026-11-09), cargo 1.100.0 (3acc79c0c 2026-11-05)

## 1. What changed

- `crates/pdfxi-security/src/encryption_writer.rs` - removed the deterministic
  `derive_file_key` / ID-derived salts / ID-derived `/Perms` padding. AES-256
  revisions 5 and 6 now draw a random 32-byte file key, two fresh 8-byte user
  salts, two fresh 8-byte owner salts, and a fresh 4-byte `/Perms` padding from
  the operating-system CSPRNG on every save.
- `crates/pdfxi-security/src/encryption_writer.rs` - every encrypted AES stream
  and string now gets its own fresh random 16-byte IV from the CSPRNG, prepended
  to the ciphertext. Identical plaintexts therefore never share a ciphertext
  prefix, including two streams in the same document (AES-256 uses one file key
  for all objects, so the IV is the only differentiator there).
- `crates/pdfxi-security/src/encryption_writer.rs` - preserves the newest
  classic trailer's `/Info` reference in protected and decrypted output.
- `crates/pdfxi-security/src/standard_handler.rs` - `/Perms` verification now
  also checks the reserved `0xFFFFFFFF` bytes required by Algorithm 10.
- `crates/pdfxi-security/src/error.rs` - `RandomnessUnavailable`, a fail-closed
  typed error when the OS entropy source fails.
- `crates/pdfxi-security/src/protect.rs` - documentation updated: the AES-256
  key is random, not password/ID-derived.
- `crates/pdfxi-security/tests/protect_document.rs` - new real-world randomness,
  `/Info`, permission, owner, removal and non-ASCII-password tests; artifacts for
  review.
- `crates/pdfxi-render/tests/pdfium_protected.rs` - independent PDFium reopen
  with the password, source-text match after normalization, `/Info` title check,
  failure without a password or with a wrong one, and a second non-ASCII
  password case.
- `crates/pdfxi-render/Cargo.toml` - `[dev-dependencies]` `pdfxi-core` and
  `pdfxi-security` for that test only. No render `src/**` was touched.

No cipher, hash, or RNG is hand-rolled. `getrandom 0.2.17` (already in the
workspace lock graph through `rand`) supplies OS entropy; licence
`MIT OR Apache-2.0`. It is now a direct dependency of `pdfxi-security`.

## 2. Exact R6 algorithm steps implemented

Revision 6 is routed through the existing `standard_handler` helpers; the writer
now supplies random inputs instead of ID-derived ones.

**Algorithm 8 - `/U` (48 bytes)**

1. Truncate the user password to 127 bytes.
2. `validation_hash = Algorithm 2.B(password || U_validation_salt)` (32 bytes).
3. `U = validation_hash || U_validation_salt (8) || U_key_salt (8)`.

**Algorithm 9 - `/UE` (32 bytes)**

1. `intermediate = Algorithm 2.B(password || U_key_salt)` (32 bytes).
2. `UE = AES-256-CBC-no-padding(intermediate, zero IV, file_key)`, where
   `file_key` is the random 32-byte key.

**Algorithm 10 - `/O`, `/OE`, `/Perms`**

1. `O = Algorithm 2.B(owner_password || O_validation_salt || U_full_48) || O_validation_salt (8) || O_key_salt (8)`.
2. `OE = AES-256-CBC-no-padding(Algorithm 2.B(owner_password || O_key_salt || U_full_48), zero IV, file_key)`.
3. `/Perms` plaintext block: `P` as 4-byte little-endian, `FF FF FF FF`,
   `'T'` when `/EncryptMetadata` is true else `'F'`, `"adb"`, 4 random bytes.
4. `Perms = AES-256-ECB-encrypt(file_key, block)`.

Verification decrypts `/Perms` with the recovered file key and checks `"adb"`,
the stored `P`, the `/EncryptMetadata` flag, and now the reserved
`FF FF FF FF` bytes. `O`/`OE` are tried only after the user password fails; both
paths verify `/Perms` before returning a decryptor.

The file key is never derived from the document `/ID` or the passwords.
`/ID` is still preserved from the source (or derived from `id_seed` when
absent); it is no longer key material.

**Revision 5.** The same wrapping code runs with the revision-5 hash (SHA-256
instead of Algorithm 2.B). Revision 5 also receives random salts and a random
file key; it is not left on the old derivation. This is a deliberate, tested
change, not a compatibility fallback.

**Revisions 2-4.** Unchanged: those revisions derive the file key from the
password and `/O`, as their specifications require. RC4 and AES-128 output
therefore remains byte-reproducible.

## 3. Where randomness comes from

`getrandom::getrandom` (v0.2.17, `MIT OR Apache-2.0`), which asks the operating
system for entropy. Per `protect_document` call:

- 32 bytes for the file key,
- 4 x 8 bytes for the user and owner validation/key salts,
- 4 bytes for the `/Perms` padding,
- 16 bytes for every AES stream or string IV (one draw per encrypted value).

Failure is `SecurityError::RandomnessUnavailable`; there is no deterministic or
weak fallback. `Debug` still redacts passwords and only shows the seed length.

## 4. `/Info` preservation

- `trailer_info_reference` reads the newest classic `trailer` dictionary, finds
  `/Info`, and accepts only the common `N G R` indirect form.
- The reference is inserted only if the referenced object is actually written,
  so the trailer cannot dangle.
- `encrypt_document` carries it into the protected trailer.
- `open_encrypted` carries it into the decrypted plaintext trailer, and
  `remove_protection`'s full save keeps it.

Limitation: an external encrypted source whose trailer is an xref stream (no
classic `trailer` keyword) is not parsed for `/Info`; pre-existing
`open_encrypted` object-enumeration limits apply there. Our protected output is
classic xref, so protect -> remove round-trips preserve `/Info`.

## 5. Tests

### 5.1 `pdfxi-security` unit tests

- `encryption_writer::tests::aes256_output_is_randomized_but_rc4_stays_deterministic`
  - two AES-256 saves of identical bytes/options differ;
  - `/U`, `/O`, `/UE`, `/OE`, `/Perms` each differ;
  - `/ID` stays the same;
  - every stream in the document has a different 16-byte ciphertext prefix
    between the two saves, not just the first stream;
  - two RC4-128 saves remain byte-identical (RC4 has no IV and a
    password-derived key).
- `encryption_writer::tests::identical_streams_receive_distinct_random_ivs`
  - a fixture with three streams of the same plaintext (objects 4, 7, 8);
  - each ciphertext carries a 16-byte IV and all three IVs differ;
  - AES-256 uses one file key for every object, so the differing prefixes prove
    fresh IVs rather than per-object keys;
  - decryption returns the same plaintext for all three.
- `encryption_writer::tests::info_reference_survives_an_encrypting_save`
  - `/Title` and `/Author` still read after decryption.
- `standard_handler::tests::perms_reserved_bytes_must_be_all_ones`
  - a `/Perms` block with a cleared reserved byte is rejected.

### 5.2 Real-world integration test

`protect_document::aes256_key_material_is_random_and_info_is_preserved`, on
`fixtures/realworld/microsoft-excel-2019-sample.pdf` with a staged title:

- two protects with identical source, passwords and permissions differ;
- all five key-dependent dictionary fields differ;
- both outputs open with the user password, report AES-256/R6/user, the
  restricted mask (modify=false, copy=false), and the original page text;
- `/Info` title and producer survive protection;
- the owner password opens as owner and allows modify;
- a wrong password is `WrongPassword`;
- `remove_protection` returns plaintext with the same text and the same
  `/Info` title.
- `protect_document::non_ascii_password_round_trips`, with
  `pässwörd-测试`: protect, open with `open_encrypted`, permissions and text,
  wrong-password and empty-password rejection, and removal with the same
  password.

### 5.3 Independent PDFium check

`crates/pdfxi-render/tests/pdfium_protected.rs`
(`cargo test -p pdfxi-render --features pdfium --test pdfium_protected`):

- protect the Excel fixture with `pdfium-t0256-password` and a read-only mask;
- `Pdfium::load_pdf_from_byte_slice(..., Some(password))` succeeds;
- PDFium page count equals the source;
- PDFium `page.text().all()` matches the source page text after removing
  whitespace/punctuation (both directions of containment), so the decrypted
  text is the same content, not merely non-empty;
- PDFium sees the `/Info` title (`PDFDocumentMetadataTagType::Title`);
- loading with `None` fails;
- loading with a wrong password fails;
- a second test protects with the non-ASCII password `pässwörd-测试`; PDFium
  opens it with that password, extracts matching text, and still refuses the
  file with no password.

Result: `2 passed, 0 failed`.

The non-ASCII password is a real interoperability result: both
`open_encrypted` and PDFium accept the raw UTF-8 bytes (`pässwörd-测试`), and a
wrong non-ASCII password is rejected by this crate.

`pdfium-render 0.9.5` maps only security revisions 2-4 in
`PdfSecurityHandlerRevision`, so the test cannot assert "R6" through that enum
(it returns `UnknownPdfSecurityHandlerRevision` for 5/6). The proof is the
successful decryption, text, metadata and the two rejection cases.

## 8. Remaining risks

- **Random IVs are now in place.** Every AES stream and string gets a fresh
  16-byte CSPRNG IV, including two streams in one document. What remains is the
  broader reader matrix: only PDFium is available here as an independent reader.
- **External xref-stream `/Info`** is not preserved on removal, because
  `trailer_info_reference` reads a classic `trailer` dictionary and
  `open_encrypted` still enumerates physical `N G obj` headers. Our own
  protected output is classic and round-trips.
- **PDFium revision reporting.** `pdfium-render 0.9.5` cannot report R5/R6 in
  its `PdfSecurityHandlerRevision` enum, so R6 is proven by successful
  decryption and text/metadata, not by a revision enum.
- **Non-ASCII passwords are tested, not universal.** `pässwörd-测试` works with
  this crate and PDFium. This is not a proof for every non-ASCII string,
  normalization form, or reader; passwords remain raw UTF-8 bytes here.
- **No second independent reader** (qpdf/Adobe) is installed in this lane.
- **Permissions remain advisory** and the owner password bypasses them; that is
  unchanged from T-0238.
- `getrandom` failure is fatal by design; there is no fallback, so a platform
  without a working OS entropy source cannot protect a document.
