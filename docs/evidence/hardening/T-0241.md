# T-0241 - produce real CMS PDF signatures with vetted crypto

Date: 2026-11-20. Lane: security. Task: T-0241 (library half of the signing pair
per ADR 0012). Acceptance: A-20, the library side only; the E-signed badge and
the request flow belong to the serialised app shell task T-0245.

Status: library-complete. `crates/pdfxi-security/src/pdf_signature.rs` signs a
real PDF with a real CMS/PKCS#7 signature over the declared byte range and
verifies it independently. Feature row SEC-005 moves to `library`, not
`verified`, because there is no GUI caller yet.

## 1. CMS structure produced

`build_cms` emits a DER `ContentInfo`:

- `ContentInfo.contentType` = `1.2.840.113549.1.7.2` (signedData).
- `SignedData.version` = 1.
- Encapsulated content type `1.2.840.113549.1.7.1` (data), content absent: the
  PDF bytes are supplied out of band through `/ByteRange`, the normal PDF
  detached convention.
- Exactly one `SignerInfo` with:
  - digest algorithm `2.16.840.1.101.3.4.2.1` (SHA-256),
  - signature algorithm `1.2.840.113549.1.1.11` (sha256WithRSAEncryption,
    PKCS#1 v1.5),
  - signed attributes `contentType` (`1.2.840.113549.1.9.3`), `signingTime`
    (`1.2.840.113549.1.9.5`) and `messageDigest`
    (`1.2.840.113549.1.9.4`), in DER SET OF order,
  - the RSA signature computed over the DER SET OF encoding of those attributes.
- One embedded certificate: 2048-bit RSA, self-signed,
  `CN=PDFXI Test Signer, O=PDFXI`, generated for tests from PEM.

## 2. PDF objects written

Signature dictionary (keys sorted by the core writer):

| Key | Value |
|---|---|
| `/Type` | `/Sig` |
| `/Filter` | `/Adobe.PPKLite` |
| `/SubFilter` | `/adbe.pkcs7.detached` |
| `/ByteRange` | `[0 <contents_start> <contents_end> <len - contents_end>]` |
| `/Contents` | reserved hex string, zero padded to the reservation |
| `/M` | PDF date of the signing time |
| `/Name` | signer subject |
| `/Reason`, `/Location` | only when the caller supplies them |

Widget annotation (invisible, still listed by readers):

| Key | Value |
|---|---|
| `/Type` | `/Annot` |
| `/Subtype` | `/Widget` |
| `/FT` | `/Sig` |
| `/T` | field name (`Signature1` by default) |
| `/F` | 132 (Locked + Hidden: the signature is not a printable appearance) |
| `/Rect` | `[0 0 0 0]` |
| `/P` | reference to the page |
| `/V` | reference to the signature dictionary |

The widget is appended to the page `/Annots` array (creating it when absent,
following a direct or indirect array) and to the `/AcroForm` `/Fields` array
(creating a minimal `/AcroForm` when absent). `/SigFlags` is set so readers
treat the file as signed.

`/Contents` is reserved (default 8192 bytes, `MIN_CONTENTS_RESERVATION`
enforced), the DER is written over the exact `<...>` window, and the remaining
bytes stay `00` so the file length never shifts after signing.

## 3. Two production bugs found and fixed

1. **Object-number allocation order.** `Document::allocate_object_number` only
   advances past objects already staged in `changes`. Allocating the signature
   and the widget number back to back returned the same number, so the widget
   overwrote the signature dictionary. Fixed by staging each object with
   `set_object` before allocating the next number; the invariant is documented
   at the allocation site.
2. **`/ByteRange` computed from placeholders.** The first draft derived the
   ranges from the placeholder offsets in the pre-save buffer. The real offsets
   are only known after the incremental save. Fixed by saving first, locating
   this revision's own `/Contents` window at or after `original_len`, then
   patching `/ByteRange`, computing the digest over the two ranges, and finally
   writing the CMS.

## 4. What `verify_signature` proves, and what it does not

Proves:

- The file contains a signature dictionary and a `/ByteRange` of four integers
  starting at 0.
- The `/Contents` decodes to a DER CMS that parses, with one signer, a SHA-256
  digest algorithm and an RSA PKCS#1 v1.5 signature algorithm.
- The RSA signature verifies over the DER SET OF signed attributes using the
  embedded signer certificate whose issuer and serial match the `SignerInfo`.
- The `messageDigest` signed attribute equals SHA-256 over the byte ranges.
- Whether the ranges cover the whole file, how many bytes follow the signature,
  the signer subject and SHA-256 fingerprint, the signing time attribute and
  `byte_range` are reported as typed fields.

Does **not** prove:

- Certificate chain trust: `certificate_chain_trusted()` returns `None`. No
  trust anchors are consulted.
- Revocation: no CRL, OCSP or any other revocation source is checked.
- Time: `signingTime` is self-asserted by the signer. There is no RFC 3161
  timestamp token, so a later backdating is undetectable.
- Appearance: the widget has no visual signature; nothing renders on the page.
- Document permissions: no `/Perms`, no DocMDP, no field-lock dictionary, and
  only one signature per revision is understood.
- Identity source: the PEM is caller supplied. There is no PFX import, no
  Windows certificate store, and no user-facing key protection.

The toy RSA in `cms::InMemorySignatureProvider` is **not** used by this path. It
is a crate-private, documented test double with a toy modulus, textbook
unpadded RSA and `u128` arithmetic; it stays quarantined and its doc comment
says it provides no authenticity.

## 5. Independent verification

`target/lanes/security/t0241-out/independent-check.ps1` verifies the artifacts
with Windows/.NET Framework 4.8 primitives only (`System.Security.Cryptography.
Pkcs.SignedCms`, `X509Certificate2`, `RSA.VerifyData`, `SHA256`), plus a small
standalone DER walker in the script. No PDFXI code is involved.

The .NET Framework 4.8 limitation: `SignedCms` decodes the bundle and reports
its structure, but the encapsulated content is empty and the PDF payload is the
`/ByteRange` concatenation, which `SignedCms.CheckSignature` cannot be given. A
detached PDF signature therefore cannot be checked with the one-line
`CheckSignature` call; the script reconstructs the content and verifies the two
independent facts instead (RSA over the signed attributes, SHA-256 over the
content).

Transcript (run on this tree, exit 0):

```text
== Windows SignedCms ==

Certificates:       1
Subject:            CN=PDFXI Test Signer, O=PDFXI
Issuer:             CN=PDFXI Test Signer, O=PDFXI
DigestAlgorithm:    2.16.840.1.101.3.4.2.1
SignatureAlgorithm: 1.2.840.113549.1.1.11
Detached:           False
SignedAttributes:   1.2.840.113549.1.9.3, 1.2.840.113549.1.9.5, 1.2.840.113549.1.9.4

== PDF /ByteRange ==
[0 92931 109317 645]  file length 109962
Content rebuilt from PDF equal to signed.content.bin: True

== CMS wire structure ==
ContentInfo.contentType:  1.2.840.113549.1.7.2
SignedData.version:       1
Encapsulated content type: 1.2.840.113549.1.7.1
signingTime attribute:    present (self-asserted, not a timestamp token)
Embedded certificate:      CN=PDFXI Test Signer, O=PDFXI
Certificate key size:      2048 bits

== BCL RSA PKCS#1 v1.5 / SHA-256 over DER SET OF signedAttrs ==
VerifyData: True
== SHA-256 over the /ByteRange byte concatenation ==
SHA-256(content) == messageDigest attribute: True

RESULT: PASS (signature valid over the declared ranges; content digest matches)
```

The equivalent OpenSSL command, for a reviewer with OpenSSL installed (not
executed here: no `openssl` binary on this host):

```text
openssl cms -verify -inform DER -in signed.cms.der -content signed.content.bin \
    -binary -noverify
```

`-noverify` is required because the certificate is self-signed; the command
still proves the signature and the digest, not the identity.

`signed.pdf` also opens through PDFium (the operator's check), so the signature
objects do not break the viewer's parser.

## 7. Tests

Eight tests in `pdf_signature::tests`, all passing:

- `signs_a_real_pdf_and_verifies_the_cms`
- `a_flipped_byte_inside_the_signed_range_is_reported_as_tampering`
- `appending_bytes_after_the_signature_is_reported_without_losing_validity`
- `a_corrupted_signature_value_is_rejected`
- `a_certificate_that_does_not_match_the_signature_is_rejected`
- `pem_loading_rejects_bad_and_undersized_keys`
- `a_pdf_without_a_signature_is_a_typed_error`
- `reserved_space_that_is_too_small_is_a_typed_error`

The positive test signs `fixtures/realworld/microsoft-excel-2019-sample.pdf`,
verifies the CMS, and writes the three artifacts above. The negative tests cover
tampering inside the ranges, appended bytes, a corrupted signature value, a
certificate mismatch, bad PEM input, a missing signature and an undersized
reservation.

## 8b. Advisory decision

Status: mitigated (scoped ignore), decided by the orchestrator on 2026-11-20.

- `deny.toml` ignores `RUSTSEC-2023-0071` with a comment block stating scope,
  reason, guard and decision record. `cargo deny check` now exits 0:
  `advisories ok, bans ok, licenses ok, sources ok`.
- Reason: the advisory is a PKCS#1 v1.5 **decryption** padding-oracle timing
  issue. `pdfxi-security` uses `rsa` only for signing and verification
  (`SigningKey<Sha256>`, `Pkcs1v15Sign`, `RsaPrivateKey::from_pkcs8_pem` /
  `from_pkcs1_pem`, `RsaPublicKey::verify`). No decryption API is present.
- Guard: `crates/pdfxi-security/tests/rsa_usage_scope.rs`,
  `rsa_is_used_for_signing_and_verification_only`, scans `src/**/*.rs` for
  `DecryptingKey`, `Pkcs1v15Encrypt`, `Oaep` and
  `rsa::RsaPrivateKey::decrypt` and fails if one appears.
- Revisit: if PDFXI adds RSA decryption, a fixed `rsa` release ships, or signing
  moves to another backend. Full record:
  `orchestration/blockers/T-0241-rsa-advisory.md`.
