## 1. Why

`pdfxi-edit` had paragraph (`paragraph_edit`) and image (`image_edit`) models but
no dependency on a real `pdfxi_core` page content stream, so no edit could reach
a saved PDF. ADR 0010 requires every edit to mutate the real document through
the core object model and save through the single core write path.

Round A adds the real vertical slice on
`fixtures/realworld/microsoft-excel-2019-sample.pdf` (hybrid xref + object
stream + Flate content + subset Calibri): a geometry-aware text model, in-place
run replacement with paragraph reflow, a wrapped text box, and PNG/JPEG image
placement. The saved output is reparsed with `pdfxi-core` and its page text is
asserted. PDFium rendering of the artifact is the orchestrator's independent
check; the path is written for it.

## 3. Text model and geometry

`text_blocks` decodes the page with `Document::page_content` (the same filters
the reader uses) and scans the content stream with a bounds-checked tokenizer.
It tracks:

- graphics state: `q`/`Q`, `cm`;
- text objects: `BT`/`ET`, `Tm`, `Td`, `TD`, `T*`, `TL`, `Tc`, `Tw`, `Tz`, `Ts`;
- font selection `Tf` and the four show operators `Tj`, `TJ`, `'`, `"`;
- marked content `BMC`/`BDC`/`EMC`, including `/P <</MCID n>>` keys.

Each run records the font resource name, font size, the text matrix in
`[a b c d e f]` order, the baseline origin from `Tm x CTM`, the decoded string,
and a baseline rectangle. Simple-font widths come from `/FirstChar` and
`/Widths`; Type0 widths come from `/W` and `/DW`. Text is decoded through the
font's `/ToUnicode` CMap when present, with the same Latin-1 fallback the core
extractor uses. Runs with marked-content paragraph keys are grouped by that key;
otherwise lines are clustered by baseline and blocks by vertical proximity and
horizontal overlap. Blocks and runs are ordered top-to-bottom, then left-to-right.

On the Excel fixture, page 1 yields separate `/P` blocks for the heading
(`PDFXI Real-World Sample`, font `F1`, 11.04 pt) and the sentence
(`The orchestra rehearsed ...`). The heading rectangle lies above and does not
intersect the sentence rectangle, and both lie inside the 612 x 792 MediaBox.

## 4. In-place replacement and reflow

`replace_run_text`:

1. Reparses the staged document through `save_incremental` (the core has no
   staged-object accessor; this is the same pattern T-0230 uses).
2. Finds the block that contains the global run index and assembles the block
   text with that run replaced.
3. Greedily wraps the text to the block width.
4. Splices the content stream: every text-showing operator in the block is
   removed and the rebuilt block is emitted at the first run's baseline. The
   surrounding operators (`re ... W* n`, `q`/`Q`, `BDC`/`EMC`, colours, graphics
   state) are not touched.
5. Replaces the page `/Contents` with one new stream containing the spliced
   bytes; resources and the page dictionary are staged copy-on-write.

Because the replacement is emitted inside the first show operator's existing
text object, the page CTM and text state at that point are still in effect. The
emitted block sets `Tc`, `Tw`, `Tz`, `Ts`, fill colour and `Tf` explicitly, so it
does not depend on earlier text state.

Limits (documented in the module):

- one font for the whole reflowed block;
- greedy word wrap, no justification, no hyphenation;
- horizontal text only (rotated text gets the correct origin but an
  axis-aligned rectangle);
- a wrapped line ends with a space so a simple extractor still sees the words
  separated;
- `replace_run_text` rebuilds the whole block, not a single glyph run inside a
  mixed-style paragraph (the first run's style wins).

## 5. Font reuse and fallback embedding

### 5.1 Round B defect, root cause and fix

The first artifact passed text extraction but PDFium rendered the replacement as
a solid black bar (and the added text box as a smaller bar). The defect was in
the generated CID font, not in the content stream:

- `/W` was built by `pdfxi_core::font::build_cid_font`, whose single-glyph form
  emits two numbers (`c w`). ISO 32000-1 `/W` only accepts `c [w1 ...]` or
  `c_first c_last w`; a reader therefore parsed `3 1228 17 1228 ...` as a range
  `3..1228` with width `17`, then further ranges. Every CID was given a tiny
  advance, so the glyphs piled onto one another at the same origin and formed a
  solid bar. The same array also used raw font units (1228) instead of
  thousandths of text space (600).
- CIDs were glyph IDs with no explicit `/CIDToGIDMap`. That is legal only when
  the reader defaults to Identity, and it leaves no place to state the mapping.

The fix assigns sequential CIDs (`1..N`, CID 0 reserved for notdef), encodes
content with those CIDs, keys `/W` and `/ToUnicode` by the same CIDs, and emits
a real two-byte-per-CID `/CIDToGIDMap` stream mapping each CID to the glyph ID
from the font's `cmap`. `/W` is rebuilt locally in the spec forms:
`c_first c_last w` for a run of equal-width contiguous CIDs and `c [w]` for a
single CID. Widths are converted from font units to thousandths with
`round(advance * 1000 / unitsPerEm)`. `/DW` stays 600 and `/Length1` is set on
the `/FontFile2` stream. CID 1 maps to glyph 3 (space), CID 2 to glyph 0x11
(period), and so on; the emitted mapping stream is
`0000 0000 0003 0011 0027 ...`.

The run's own font is still preferred when it is a simple (one-byte), non-subset
font with a WinAnsi/MacRoman/Standard/PDFDoc encoding and every character is in
its width table. The Excel fixture uses `BCDEEE+Calibri`, a subset, so
replacement embeds the fallback and the outcome reports
`FontChoice { embedded: true, base_font: "CourierPrime", .. }`.

Asset and licence:

- `crates/pdfxi-edit/assets/CourierPrime-Regular.ttf` (71,188 bytes), Courier
  Prime Regular, Copyright 2015 The Courier Prime Project Authors.
- `crates/pdfxi-edit/assets/CourierPrime-OFL.txt` (4,403 bytes), SIL Open Font
  License 1.1. Redistribution is permitted by the OFL; the integrator should add
  the asset to `NOTICE`.

Embedding details:

- The font is parsed by a local TrueType reader (`cmap` formats 0, 4, 6 and 12;
  `head`, `hhea`, `hmtx`, `maxp`). Every table offset and length is
  bounds-checked and failures are typed.
- The program is embedded **in full** (no subsetting) through
  `pdfxi_core::font::build_cid_font` / `stage_cid_font` as a `/Type0` font with
  a `/CIDFontType2` descendant, `/FontFile2`, a `/CIDToGIDMap` stream and a
  generated `/ToUnicode` CMap. Only used CIDs are listed in `/W` and the CMap.
  `/Length1` is added to the font stream, which the core builder does not set.
- Each add/replace operation embeds its own font with the CID assignment used by
  that operation; this avoids a stale CID map when a later edit introduces a
  character the first assignment did not contain.
- No external dependency was added to the library: the PNG inflater reuses the
  core `FlateDecode` path, and the TrueType/CMap work is local. `pdfxi-render`
  with the `pdfium` feature is a **dev-dependency only** for the render proof;
  it brings `pdfium-render` (MIT) transitively and loads the native PDFium
  library at runtime.

## 6. Added text and images

`add_text_box` wraps each newline-separated paragraph to the rectangle width
using the fallback font, applies left/centre/right alignment, and appends a new
content stream (`q ... BT ... ET Q`) so existing page content is untouched. The
rectangle must lie inside the page MediaBox.

`add_image` accepts:

- PNG: signature, `IHDR` (8-bit greyscale/RGB/RGBA/grey+alpha/palette), `PLTE`,
  concatenated `IDAT`, zlib inflate through `pdfxi_core::decode_stream`, then
  the five PNG scanline filters (None/Sub/Up/Average/Paeth). Alpha is ignored
  for round A (no `/SMask`). Output is an unfiltered eight-bit `DeviceGray` or
  `DeviceRGB` image XObject.
- JPEG: SOF dimensions and component count are read; the original bytes are
  embedded unchanged with `/Filter /DCTDecode` (`DeviceGray`, `DeviceRGB` or
  `DeviceCMYK`).

Both append a content stream and a `/XObject` or `/Font` resource, preserving
the existing resource dictionaries and contents array.

## 10. What is left

- A-17 now has a library path; the app shell task still owns the UI and the
  `verified` row.
- A-23 is partial: add text and add image are real. Move, resize, replace and
  delete of existing text/image objects are still model-only
  (`image_edit`, `paragraph_edit`), and no object-picking/hit-test API exists.
- The fallback is embedded in full per operation; subsetting the font program or
  sharing one CID assignment across pages is a follow-up.
- Alpha PNG is flattened (alpha ignored); `/SMask` and CMYK PNG are follow-ups.
- Reflow is single-font, horizontal only, greedy, and block-scoped.
- The shell must pass the `pdfxi-document` session bytes through the core
  document/reparse path; no session type is depended on here, matching T-0230.
