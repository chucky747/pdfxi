## 2. Trust model

1. Anchors come only from the caller's bundle. There is no built-in root set, no
   OS default, no network, and no host clock.
2. Path building is the existing `x509::verify_chain`: signature over the exact
   `tbsCertificate`, validity at the caller's clock, CA basic constraints,
   `keyCertSign`, path length, EKU intersection, and unknown critical
   extensions.
3. A chain is trusted only when its last certificate is byte-for-byte one of the
   configured anchors (`TrustStore::is_anchor`). A valid signature under an
   unconfigured issuer is `Some(false)`, not trust.
4. The outcome is deliberately three-valued:

   | State | `trusted()` | Reason |
   |---|---|---|
   | Path reached a configured anchor | `Some(true)` | `None` |
   | Anchors configured, no path reached one | `Some(false)` | typed `TrustFailureReason` |
   | Bundle empty | `None` | `None` (not evaluated) |

   `None` is not "trusted" and not "untrusted". A caller that has not configured
   anchors must show trust as unverified.

5. All decisions are deterministic for a given input, certificate set, verifier,
   and `now`.

### Typed failures

Trust and validity failures are decisions, so they are reported in
`ChainTrustReport::reason()` through the existing `TrustFailureReason`:
`NoAnchor`, `IssuerUnknown`, `ChainTooLong`, `SignatureInvalid`, `Expired`,
`NotYetValid`, `NotCa`, `KeyUsageViolation`, `EkuMissing`,
`UnknownCriticalExtension`, and `MalformedCertificate`. Structural input
problems (bad DER, malformed PEM, a file that cannot be read) return
`SecurityError`; a new `SecurityError::TrustAnchorInvalid(&'static str)` names
the loader step without carrying bytes or paths.

### Real RSA verifier

`x509::RsaPkcs1Verifier` is a production `CertificateVerifier` for RSA issuer
keys. It verifies `sha256/384/512WithRSAEncryption` PKCS#1 v1.5 signatures over
the exact TBS bytes, returns `Ok(false)` for a mismatch or a non-RSA/unknown
algorithm, and stores no key.

### PEM/DER loader

- PEM: a bounded block scanner accepts LF or CRLF, a UTF-8 BOM, arbitrary base64
  line lengths, and multiple `CERTIFICATE` blocks; non-certificate blocks are
  ignored. Bodies are decoded by a strict standard-alphabet base64 decoder and
  parsed as X.509 DER. Empty/whitespace-only input is rejected before parsing.
- DER: one certificate, or a concatenation of certificate TLVs.
- Files: read through `std::fs`; failures map to `Configuration` without a path
  in the error value.
- Why not the dependency PEM helper: the committed T-0249 PEM fixtures wrap
  bodies at 76 columns, and the strict RFC 7468 helper rejects non-64-column
  bodies. The scanner above accepts both and is covered by the real-fixture
  tests.

## 3. Certificate-parser corrections required by real certificates

The committed T-0249 PEMs are real Windows-generated certificates. Two strict
parser assumptions had to be corrected before the real chain could be used:

1. **Wide serial numbers.** RFC 5280 allows serials up to 20 octets; all three
   fixtures use 16-octet serials. `Certificate::parse` now validates a positive
   canonical `INTEGER`, caps the magnitude at 20 octets, stores the full bytes,
   and exposes `serial_number_bytes()`. The legacy `serial_number() -> u64`
   returns the low 64 bits for a wider serial and is documented as a view;
   `serial_number_bytes()` is the identity. Small serials are unchanged.
2. **SAN and EKU extnValue double-unwrapping.** `parse_extension` already
   unwraps the extension `extnValue` `OCTET STRING`, but `parse_subject_alt_name`
   and `parse_extended_key_usage` unwrapped it a second time and rejected every
   conforming SAN/EKU extension. Both now parse the payload directly. The
   synthetic builders in `x509/tests.rs` and `timestamp.rs` were corrected in
   the same change; `extension_parsing_rejects_malformed_payloads` still proves
   malformed payloads are rejected.

Both are regression-tested by the real fixture chain and by the existing x509
and timestamp suites.

## 6. Limits and remaining work

- **Real Windows store enumeration is not implemented.** The security crate has
  no `windows` dependency and this round must not change the shared workspace
  lock file, so adding the FFI would not be a scoped, portable change. The
  trait, metadata type, and `WindowsStoreUnavailable` result are the seam; a
  Windows-backed implementation belongs in `certificate_store.rs` behind the
  same trait, with its unsafe boundary documented in that one module.
- `SignatureVerification::certificate_chain_trusted()` still reports `None`.
  This round provides `TrustAnchorBundle::certificate_chain_trusted`; wiring the
  bundle into `verify_signature` and the sign panel is a later shell/wiring task.
  Nothing in this round claims trust from an unevaluated signature.
- Round B: RFC 3161 timestamp token validation against a deterministic fixture,
  CRL/OCSP revocation with typed good/revoked/unknown/unavailable reasons, and
  the real Windows certificate-store enumeration and key handles. None of those
  is claimed here.
- A-20 and the security feature rows are not promoted. The existing trust
  manager CRL model is unchanged and still Round B.
