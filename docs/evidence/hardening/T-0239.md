## 1. What shipped

- `crates/pdfxi-convert/src/pdf_export.rs` — new end-to-end bridge from a parsed
  `pdfxi_core::Document` to the existing writers:
  - `export_text(&Document, &PdfTextOptions) -> Result<String, PdfExportError>`
    extracts through `Document::page_text` (ToUnicode applied), honours the
    shared zero-based page selection, and offers `LineFeed`, `BlankLine` and
    `FormFeed` separators plus one-based page headings.
  - `build_office_document(&Document, title) -> Result<OfficeDocument, ...>`
    maps each page to an `OfficePage` with the real media-box size and one
    paragraph per extracted line.
  - `export_docx(&Document, &PdfDocxOptions) -> Result<OfficeExport, ...>`
    writes a real WordprocessingML package through the existing
    `DocxExporter` and returns its validated bytes and report.
  - `PdfPageSeparator`, `PdfTextOptions`, `PdfDocxOptions`, `PdfExportError`.
- `crates/pdfxi-convert/src/lib.rs` — public re-exports. The previous
  `(page, text)` iterator writer is still available as `export_page_text`;
  `export_text` is now the document-level entry point requested by A-27.
- `crates/pdfxi-convert/src/office_export/docx.rs` — two writer fixes found by
  opening the output: wide pages now declare `w:orient="landscape"`, and the
  bullet numbering marker is a real U+2022 instead of the literal text
  `\u2022`.
- `crates/pdfxi-convert/src/office_export/mod.rs` — the already-present
  deterministic stored-ZIP reader is crate-visible so the export tests can
  validate their own archives. No external `zip` crate was added.
- `crates/pdfxi-convert/tests/export_adapters.rs` — import updated to
  `export_page_text`; no behavioural change.
- `orchestration/feature-updates/T-0239.toml` — matrix fragment for
  EXPORT-001 and EXPORT-005.

No new dependency: the crate already contained a deterministic stored-ZIP
writer/reader (`src/office_export/zip.rs`, MIT-compatible in-repo code) and
already depended on `pdfxi-core`. `Cargo.toml` was not changed and no workspace
entry or lockfile package was needed.

## 3. Fidelity limits declared in code

- Text is exactly what `pdfxi_core::Document::page_text` returns. That extractor
  emits line breaks only for the PDF `'` and `"` operators; it does not expose
  glyph coordinates. Pages whose content uses only `Tj`/`TJ` therefore become
  one paragraph. Position-based line/paragraph reconstruction needs a separate
  geometry extractor and is not claimed in round A.
- DOCX contains text only. Images, vector art, annotations and page backgrounds
  are not embedded and are not silently approximated.
- XLSX and PPTX writers already exist in `office_export` but are not wired to a
  real `Document` in this round. Image, HTML and RTF end-to-end export are also
  round B.
- Word was not automated on this host. The package was validated structurally
  (ZIP CRC + required parts + OPC + XML parse); the operator will open the
  artifacts in Word.
