## Review follow-up (HIGH conformance defect)

A reviewer found that image XObject streams omitted the mandatory `/Length`
entry required by ISO 32000-1. Text streams already received it through
`stream_object`, but PNG and JPEG image dictionaries were assembled without it;
the lenient `pdfxi-core` parser masked the omission, and an image payload
containing the bytes `endstream` could be truncated by a strict reader. Fixed by
computing the exact embedded byte count at parse time and including `/Length`
in both image stream dictionaries: the concatenated `IDAT` payload for PNG and
the whole JPEG file for JPEG. Three regression tests now parse the emitted PDF
bytes directly and check the declared `/Length` against the actual bytes between
`stream\n` and `\nendstream` for PNG and JPEG, plus a JPEG whose payload contains
an embedded `\nendstream` sequence. The task was re-claimed for the fix and all
four checks were rerun; the numbers below are from that rerun.

## Notes on the fixes made during verification

- The first `cargo test` run failed to compile because the Helvetica AFM width
  table declared 95 entries but supplied 94 (the digit `9` advance width was
  missing). Added the missing `556`; all tests then passed.
- One integration assertion initially expected `/Size 9`; a one-page text PDF
  has seven in-use objects plus the free-list head, so the correct value is 8.
  The assertion now records this with a comment and passes.
- `rustfmt` reformatted `lib.rs` and `tests/create_pdf.rs`; `cargo fmt
  -p pdfxi-convert -- --check` is clean afterwards.
- rustdoc initially rejected a redundant explicit intra-doc link target in
  `lib.rs` (`[`CreateError`](create::CreateError)`); simplified to
  [`CreateError`] (the crate-root re-export), after which the doc build passed.
