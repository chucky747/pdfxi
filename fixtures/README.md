# Fixtures

This directory holds PDF fixture data used by PDFXI's tests and benchmarks.

## Committed fixtures

Only **small, deterministic, text-based fixtures** are committed to this
repository. They are generated by the builders in `pdfxi-testkit` (see
`crates/pdfxi-testkit/src/lib.rs`) and are safe to check in because they contain
no real user data, credentials, or copyrighted material. A committed fixture must:

- be reproducible from a builder or a documented checksum;
- stay small (a few kilobytes at most);
- contain synthetic text only — never a customer document.

Examples include the single-page `minimal.pdf` used by the CLI smoke test.

## M1 committed corpus (50 fixtures)

`fixtures/manifest.toml` lists exactly **50** committed fixtures (T-0024),
totalling ~68 KiB — well under the 200 KiB corpus budget. The set covers:

- **Page counts** 1 / 2 / 3 / 10 / 100, plus the structural edge cases 0 and
  4–9 (`multipage-*.pdf`).
- **Page sizes** Letter, A4 (integer and fractional), landscape, A3/A5/B5,
  legal/tabloid/ledger/executive, tiny (`72x72`), micro (`10x10`), square, and
  large/poster (`size-*.pdf`).
- **Text variants** plain ASCII, punctuation, long strings, digits, symbols,
  mixed case, and the distinct per-page text of multipage documents
  (`text-*.pdf`).
- **Structural baselines** `minimal.pdf`, `text.pdf`, and `multipage-3.pdf`
  whose names and bytes have been stable since T-0016.

The manifest and all PDF bytes are regenerated together from one description:

```text
cargo run -p pdfxi-testkit --example generate_fixtures
```

The generator writes every file and recomputes each SHA-256 from the bytes it
wrote, so hashes, builders, page counts, and text markers cannot drift from the
files. The integration test `crates/pdfxi-testkit/tests/committed_fixtures.rs`
verifies every hash, page count, text marker, the corpus size budget, and that
regeneration is byte-identical.

## M2 authoring corpus (6 fixtures)

`fixtures/authoring-manifest.toml` lists **6** deterministic fixtures under
`fixtures/authoring/` (T-0064). Each entry records its file name, primary
`feature`, searchable `tags`, `pages`, exact byte `size`, and SHA-256 `sha256`.
The set covers:

- **Page boxes** — all five boxes (Media/Crop/Bleed/Trim/Art) on one page with
  distinct values (`authoring-page-boxes.pdf`).
- **Rotation** — three pages carrying `/Rotate` 90, 180 and 270 degrees
  (`authoring-rotation.pdf`).
- **Page labels** — a three-page document with a `/PageLabels` number tree
  (`authoring-page-labels.pdf`).
- **Annotations** — `/Text`, `/Highlight`, `/Link` and `/Widget` dictionaries
  (`authoring-annotations.pdf`).
- **Forms** — an `/AcroForm` with `/Tx`, `/Btn` and `/Ch` fields
  (`authoring-forms.pdf`).
- **Encryption** — a standard-security-handler revision 2 sample
  (`authoring-encrypted.pdf`).

Regenerate all six files and the manifest from the single source of truth:

```text
cargo run -p pdfxi-testkit --example generate_authoring_fixtures
```

The generator computes sizes and digests from the bytes it writes, so the
manifest cannot drift from the files. `crates/pdfxi-testkit/tests/authoring_corpus.rs`
verifies manifest integrity, checksum stability, parsing through
`pdfxi_core::Document`, every feature value, and byte-identical regeneration.
Golden helpers in `pdfxi_testkit::golden` record stable structural snapshots.
`ContentSnapshot` preserves every content-stream byte except trailing ASCII
whitespace. `PageTreeSnapshot` records exactly three facts per page — object
number, the five page-box arrays, and `/Rotate` — and first strips the
documented volatile dictionary keys `/CreationDate`, `/ModDate`, `/ID` and
`/Producer` with `normalize_volatile_fields`. Other dictionary entries are out
of scope for the snapshot rather than normalized; changes to any recorded field
are detected by `fingerprint()`.

### Encrypted fixture password (public test value only)

`authoring-encrypted.pdf` uses a **documented, public** test password so the
corpus contains no secret. The user password is `pdfxi-test` and the owner
password is `pdfxi-owner` (constants `TEST_USER_PASSWORD` and
`TEST_OWNER_PASSWORD` in `pdfxi_testkit::authoring`). The `/O` and `/U` values
are derived deterministically from those constants with the R2 algorithm; the
test proves the documented password is accepted and a wrong one is rejected.
The sample exists for parser recognition of `/Encrypt` and `/ID` only — never to
protect real data.

## Generated fixtures

All fixtures are **generated in memory at test time** by `pdfxi-testkit`:

- `minimal_pdf()` — a single page showing `Hello, PDFXI!` (612 x 792 pt).
- `text_pdf(text)` — a single page showing the supplied text.
- `multipage_pdf(pages)` — exactly `pages` pages, each labelled
  `Page N of TOTAL`.
- `pdf_with_page_size(width, height)` — a single page with a custom media box.

Every builder returns a `Vec<u8>` and writes nothing to disk, so tests never
dirty the repository. Cross-reference offsets and stream `/Length` values are
computed from the real byte lengths, making the bytes structurally valid PDFs.

## Performance harness

`cargo run -p pdfxi-testkit --example bench_open --release` opens every
committed fixture 20 times (1000 opens total), reporting min/median/max wall
time in a stable format. It has no sleeps or third-party benchmark dependency
and fails only if a generous 2-second total budget is exceeded. The harness
defines "open" at the testkit level (read bytes + header/trailer/`startxref`
structure check) to avoid a `pdfxi-testkit` → `pdfxi-core` dependency cycle;
see the example source for details.

## 500-page open benchmark (M1 gate)

The M1 exit gate requires a 500-page document to open in under 1.5 s and reach
its first page in under 300 ms. That PDF is **never committed**: it is built
deterministically at run time by `pdfxi_testkit::bench::large_pdf()` and written
to `target/perf/bench-500-pages.pdf` by `write_500_page_pdf(path)`. The fixture
has 500 distinct ASCII text markers and cycles through Letter, A4, Letter
landscape and Legal media boxes; it stays below a documented 2 MiB cap.

Run the real-parser benchmark from anywhere:

```text
cargo run -p pdfxi-core --example bench_open_500 --release
```

It opens the generated bytes with `pdfxi_core::Document::from_bytes`, measures
(a) open/parse, (b) page-zero access plus text extraction and (c) a full text
pass over all 500 pages, using seven fixed iterations and no sleeps. It prints
a stable machine-readable report (`iterations=`, `open_median_ms=`,
`first_page_ms=`, `all_pages_ms=`, `pages=`, `bytes=`, then `PASS` or `FAIL`).
A budget violation prints `FAIL` and exits non-zero with the actual numbers.

## Real-world corpora

Large or third-party corpora (for example veraPDF or public-domain document
sets) are **not** committed. They are fetched on demand by checksum into a
cache outside the repository and referenced by descriptors in `corpus/`.
Fuzz seeds live beside their targets and are likewise generated or
checksum-verified rather than pasted from proprietary documents.

## Adding a fixture

1. Prefer a builder in `pdfxi-testkit` over a new binary file.
2. If a binary fixture is unavoidable, add a source/checksum note in this file
   and keep the file under a few kilobytes.
3. Never add secrets, keys, tokens, or private documents.
